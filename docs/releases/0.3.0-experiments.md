## User outcome

Execute and review a controlled, finite experiment in which every planned case is accounted for ([OUT-03](../spec.md#users-and-outcomes)).

## Included scope

- `trialfolio experiment <config> --out <dir>` for a `kind: experiment` configuration.
  - The configuration declares the experiment's purpose and one explicit baseline screen, as in 0.1.0.
  - It lists a small set of predefined variants, each changing verified settings only. Candidates are maximum holdings, rebalance frequency, a liquidity rule, slippage, and universe restrictions written as screen rules, such as a microcap cutoff, limited to types whose support 0.1.0 or 0.3.0 has verified.
  - Variants follow the default variant set ([P-13](../spec.md#proposed-defaults)) where the configuration doesn't list its own. Every variant value is one that [D-20](../spec.md#decisions) has verified. The universe isn't a variant: it's the baseline's, and another universe is a separate experiment ([D-19](../spec.md#decisions)).
  - It declares any prior research (see Required behavior).
- Compilation of all cases into fully resolved configurations before execution. Each case has a `case_key` and a `case_id`, and each attempt has an `attempt_id`.
- One approved plan covering every case and the whole request budget.
- Sequential execution, with progress saved after each case.
- Resume that skips verified completed cases, records uncertain completion separately, and never repeats a potentially charged request automatically.
- Plan revisions when the configuration changes.
- A lock that prevents two processes from running the same experiment, and per-account serialization of shared-state operations.
- An experiment report that shows every case and its outcome.

## Explicit exclusions

- Automatic search, adaptive variant generation, and optimization.
- Parallel or scheduled execution.
- Statistical acceptance decisions or ranking cases by "best".
- Variant types without recorded backend support.
- Descriptive return analytics, which is its own increment in the [roadmap](../roadmap.md#after-030).

## Supported inputs and examples

```text
trialfolio experiment study.yaml --out runs/study/
```

Running the same command against the same output directory resumes the experiment.

## Required behavior

1. **Compile, then approve.** Resolve every case before any request. Show every case, its `case_id`, and the total budget. Require one approval of the plan hash for the whole experiment.
2. **Record research context.** Record the experiment's purpose, the planned cases, and any declared prior research, meaning earlier outcome-informed work on the same idea, including work done outside Trial Folio. Record it as the user supplied it, with the status complete, partial, or unknown. Trial Folio cannot verify it and says so.
3. **Execute sequentially.** Save each attempt atomically before starting the next case. Stop before exceeding the budget.
4. **Resume safely.** On restart, skip cases with a verified `succeeded` attempt, and mark any `running` attempt without a durable response as `unknown`.
   - Do not repeat `unknown` cases automatically. Repeating one requires an explicit user action that names the case and acknowledges a possible repeat charge. It creates a new attempt of the same case.
5. **Revise explicitly.** If the configuration changes, fail with `plan.changed` unless the user approves a plan revision.
   - The revision records its reason and the new hash.
   - A case whose resolved configuration changed gets a new `case_id`, and the old case and its attempts stay in the record.
   - A case whose resolved configuration did not change keeps its identity and completed attempts.
6. **Account for every case.** Planned cases = succeeded + failed + skipped + unknown + not yet run. The report and manifest show each count, and every case appears in the report.
7. **Keep execution separate from usefulness.** The report never orders or highlights cases by performance as a selection. Statistical validation and trading readiness read "Not assessed".

## Failure and incomplete-data behavior

| Situation | Behavior |
|---|---|
| A case fails | Recorded, and execution continues with the next case. The command ends with `execution.partial`, exit 6. |
| Interrupted | Progress so far is durable. Rerunning resumes. |
| Uncertain completion | The case is `unknown`, reported separately, and not repeated automatically |
| Configuration changed since the plan | `plan.changed`, exit 3, unless a revision is approved |
| Another process holds the lock | `experiment.locked`, exit 4 |
| Budget would be exceeded | Stops before the request; the remaining cases stay not yet run |

## Required outputs

`manifest.json`, `experiment.json`, `plan.json` with its revisions, and `cases/<case_id>/attempts/<attempt_id>/` for every attempt. Also normalized CSVs covering all cases, `report.html`, and `logs/`.

## Acceptance criteria

| ID | Criterion |
|---|---|
| R03-AC01 | Every case is compiled and shown with its `case_id` before any request |
| R03-AC02 | Case identities are stable across restarts, and attempt identities are distinct |
| R03-AC03 | The declared purpose, planned cases, and prior-research status are recorded in `experiment.json` |
| R03-AC04 | An interruption after case *n* resumes at case *n + 1*, with no repeated provider call, using a test double |
| R03-AC05 | A failed case is recorded, later cases still run, and the exit code is 6 |
| R03-AC06 | Restart skips verified completed cases and flags an attempt with uncertain completion, which is not repeated |
| R03-AC07 | A changed configuration produces `plan.changed`. An approved revision gives the changed case a new identity and keeps the old case. |
| R03-AC08 | The counts add up: planned = succeeded + failed + skipped + unknown + not yet run, in the manifest and the report |
| R03-AC09 | A second process fails with `experiment.locked` |
| R03-AC10 | Execution stops before exceeding the approved budget |
| R03-AC11 | The report lists every case with its outcome and shows no performance-based selection |
| R03-AC12 | A recorded opt-in live check runs a small experiment, with the owner's credentials and a declared budget |
