### What R03-T01 verified

On 2026-10-07, R03-T01 ran five live checks, with the owner present and a budget of 35 credits, and used 25 ([run record](../../reference/variant-capabilities/README.md)). Each was a `trialfolio run` that changed one setting from its baseline, and a `trialfolio review` compared it with that baseline. Before the checks, the owner decided:

- **What verified means.** A variant type is verified only when Portfolio123 accepts its value and at least one metric changes against its baseline. That's now part of [D-20](../spec.md#decisions).
- **Holdings.** The [0.2.0 live exercise](../../reference/review-live-exercise/README.md)'s run with 50 holdings counts as the evidence for holdings.
- **The broad universe.** The microcap and slice checks used `Easy to Trade US`, a universe Portfolio123 provides, since a microcap rule on SP500 would remove nothing.

**The variant types 0.3.0 may offer.** Each changes one setting of the baseline screen to a value the [verified values](../contracts.md#screen-configuration) allow. R03-T02 limits an experiment's variants to these types:

| Variant type | Setting | Evidence |
|---|---|---|
| Maximum holdings | `max_holdings` | The 0.2.0 live exercise: 50 against 25, and 10 of 20 metrics changed |
| Rebalance frequency | `rebalance_weeks`: 1 or 4, [P-13](../spec.md#proposed-defaults)'s defaults, and no other value | R01-T01 (4) and R01-T05 (1), each a run whose results differ |
| Slippage | `slippage_percent` | R03-T01: 0.5 against 0.25, and 9 metrics changed |
| A liquidity rule | `rules`: a rule's threshold changed | R03-T01: `AvgDailyTot(30)` above 100 million dollars against 1 million, and 10 metrics changed |
| A universe restriction written as a screen rule | `rules`: a rule added, such as a microcap cutoff | R03-T01, on `Easy to Trade US`: `MktCap > 300` added, and `Mod(StockID,4) = 0` added, and each changed 10 metrics |

In these checks, the metrics that didn't change were the coverage, the risk samples, and the benchmark's own, and for slippage `r_squared` too. That's what these checks showed, not what every variant leaves alone: a rebalance variant changes `coverage_periods`, as [R01-T05](../../reference/p123api-screen-backtest-values/README.md#checks-against-the-response-layout)'s 523 weekly periods against 131 every 4 weeks show. Both rule variants change the one `rules` setting; how a variant writes its rules is R03-T02's.

**Not offered:**

- **The universe.** It's the baseline's, and another universe is a separate experiment ([D-19](../spec.md#decisions)). The run on `Easy to Trade US` was a baseline, not a variant.
- **Values not yet verified,** such as `rebalance_weeks` 2, `max_holdings` 0, and the other transaction prices and point-in-time methods ([verified values](../contracts.md#screen-configuration)).
- **A rank-drop sell rule,** and so METH-09.4's practitioner variant. Sell rules in screen backtests are unverified; the [roadmap](../roadmap.md#driving-use-case-coverage) leaves them to Simulation review.
- **Universe slices, and so METH-09.4's slice variant,** until `StockID`'s stability is verified. A `Mod(StockID,4)` rule is an added rule like any other, but 0.3.0 doesn't offer or label it as a slice (see the [open questions](#open-questions)).

**What it settles.** Microcap exclusion and universe slices can each be written as an added screen rule, and Portfolio123 accepted one of each. So microcap exclusion is in scope for 0.3.0 as a rule variant, with its cutoff stated, as [methodology's open question](../methodology.md#open-questions) on the microcap cutoff and universe-slice rule recommends. Slices aren't, yet: one backtest of one slice can't show that `StockID` stays the same for a stock across the test period, which [METH-09.5](../methodology.md#meth-09-reproducing-published-research) requires before a study relies on the slices, and that open question requires before those variants run. That's a new [open question](#open-questions).

**The owner's confirmation.** On 2026-10-07, after R03-T01's review, the owner confirmed the variant types above and what isn't offered, and the `StockID` question's default: 0.3.0 doesn't offer slices until `StockID`'s stability is verified. R03-T02 builds on them as confirmed.

### What R03-T02 specified

On 2026-10-07, R03-T02 specified the [experiment configuration](../contracts.md#experiment-configuration), schema version 1.0.0, in contracts.md:

- **One file.** The baseline's settings are written under `baseline`, with a screen configuration's keys, rules, and verified values, but without its `kind`, `schema_version`, `title`, and `purpose`. So one file holds every case ([open questions](#open-questions)).
- **The research context.** `experiment_id`, `title`, `purpose`, and `prior_research` are required. A screen's `purpose` is optional, but an experiment's is part of its research history, which R03-AC03 records; the alternative was to keep it optional, as a screen's is. The prior-research declaration is a `status`, `complete`, `partial`, or `unknown`, and a free-text `description`, required with the first two, as the [open question](#open-questions) recommended.
- **Variants.** `variants` maps a setting to a list of variants of it, as P-13's "values the configuration lists for a setting" reads. Each variant changes one setting: `max_holdings`, `rebalance_weeks`, or `slippage_percent`, to a `value`; or `rules`, by replacing one of the baseline's rules (`replace` and `with`) or adding one (`add`). Those are exactly the types R03-T01 verified, so removing a rule isn't offered. Each variant has a `key`, its case's `case_key`, and may have a `description`.
- **The default variant.** Where `variants` doesn't list `rebalance_weeks`, P-13's default adds a variant for the rebalance frequency the baseline doesn't use, keyed `rebalance-weeks-1` or `rebalance-weeks-4`. An empty list turns it off, as a paper reproduction's configuration does. So an experiment that lists no rebalance variant has one more case than it lists, which costs 5 credits at the documented cost.
- **Cases.** The baseline's case key is `baseline`. Cases come in the screen settings' order, so the order of keys in the file leaves no trace in the plan. No two cases may resolve to the same settings, and an experiment has at least one variant. A case's `case_id` is the one a screen run with the same settings has.
- **Empty lists.** An empty list is accepted only for `rebalance_weeks`, where P-13 gives it a meaning. Elsewhere, a key with no entries is left out, as a review's `intended_changes` is.
- **The budget.** `budget.provider_requests`, at least the number of cases, bounds the requests the experiment sends, across every `run` that resumes it. That's how the release's "whole request budget" and its failure row for an exceeded budget read: a budget that started again with each `run` would bound nothing. It's in requests, not credits ([open questions](#open-questions)).
- **Validated examples.** The example's five cases, and a second example's two, each resolve to a request Portfolio123 accepted, in R01-T01, R01-T05, the 0.2.0 live exercise, or R03-T01. A check with Trial Folio 0.2.1's YAML reader and screen model confirmed it ([experiment example](../contracts.md#experiment-example)).

**Left for R03-T03:** how plan 1.1.0 and `experiment.json` record the research context, the variants, and the budget; the budget's bound on authentication calls, and how its counts carry across resumes and revisions; and whether a changed `experiment_id`, case key, or description is a plan revision.

**For R03-T05:** a test that repeats the example's validation against this format, as `test_documented_example_resolves_to_reference_request` does for the screen example, and the invalid experiment configurations its test pairing needs.

R03-T02 also added three [open questions](#open-questions): whether the baseline is written in the file or named by a path, whether the budget is in requests or credits, and whether the prior-research statuses should match METH-03.4's.

**The owner's confirmation.** On 2026-10-07, after R03-T02's pull request merged, the owner confirmed everything above, and the defaults of the four [open questions](#open-questions) it answered or added: the prior-research declaration's form, the baseline written in the file, the budget in provider requests, and `partial` in [METH-03.4](../methodology.md#meth-03-research-history-and-multiple-testing) too, which now says so. That includes the default rebalance variant, which adds one case, and 5 credits at the documented cost, to an experiment whose `variants` doesn't list `rebalance_weeks`: a list replaces it, and an empty list turns it off. R03-T03 builds on them as confirmed.

### What R03-T03 specified

On 2026-10-07, R03-T03 specified plan 1.1.0 and its revisions, in [experiment plans and revisions](../contracts.md#experiment-plans-and-revisions), and the experiment's records, in [experiment output](../contracts.md#experiment-output):

- **Plan 1.1.0.** A 1.0.0 plan's fields, with the experiment's research context, every case with its `case_key`, `description`, and `variant`, and `revises`, the hash of the plan it revises. A screen keeps its 1.0.0 plan, so a screen run's artifacts don't change. `case_id` covers only a case's settings, as before, while the plan hash covers everything the plan holds. Because of `revises`, approving a revision approves replacing that particular plan; the alternative, leaving `revises` out, would keep a configuration's hash the same in every directory.
- **What's a revision.** Anything a plan holds that changes: a case's settings, an added or removed variant, the research context, a case key or description, a case's `variant` even when its settings stay the same, the order of one setting's variants, the budget, or a version of Trial Folio, `p123api`, `requests`, or `urllib3`, as the [open question](#open-questions) recommended. A comment or the file's layout isn't, since no plan records it. A case whose settings didn't change keeps its `case_id`, and so its attempts, whatever its key or plan; one whose settings changed is a new case, and the old one is retired, with its attempts kept and counted. Another `experiment_id` isn't a revision: it's another experiment, which can't run in the directory (`output.not_empty`). Nor is another universe, which [D-19](../spec.md#decisions) makes a separate experiment, so it's `output.not_empty` too. The alternative, a revision, would retire every case and keep it, so one experiment would hold cases on two universes, which D-19 doesn't allow through 0.3.0.
- **Approving a revision.** It needs a reason, given with `--revision-reason`, and the approval of its hash. Without both, `run` fails with `plan.changed`; and a reason with no revision fails with `plan.approval_required`, unless it's the reason the current plan recorded, so that the command that approved a revision, run again after an interruption, resumes it. The alternative fails that command, and asks for it without the reason. An invalid reason, such as an empty one, is a usage error from the parser, exit 2, as a blank `--out` is, and the plan display escapes a reason's control characters, as it does the configuration's text. Resuming the same plan needs its approval again, by the same hash, so the same command resumes the experiment. A resume builds the plan with the current plan's `revises`; if it isn't the current plan, the revision is that plan with `revises` set to the current plan's hash.
- **The budget across runs.** The current plan's budget bounds the whole experiment: every attempt of every case, retired cases included, under every plan and in every run. Its `authentication_calls` equals `provider_requests`, and counts every call of Trial Folio's own authentication, whatever its result. An attempt writes an authentication record, `authenticating.json`, durably before it authenticates, so a call is counted even when the process is killed before the call's exchange is recorded. A resume records such an attempt as `failed`, not possibly charged. The alternative, counting only the exchanges in start and attempt records, would lose that call.
- **The layout.** `experiment.lock` claims the directory. Each approved plan is a new `plans/<n>/`, with its configuration, `plan.json`, and `experiment.json`, written last, and nothing is sent under a plan before its `experiment.json` is written. Each run that passes its checks reserves a new `sessions/<s>/` with its session record, `session.json`, before it writes any other record or sends anything, and writes its report and then its manifest there when it ends, because no file is ever replaced, so a manifest can't be rewritten in place. So a run that stops before its end always leaves a session newer than every manifest, and the output reads as incomplete. The alternative, a session written only at the end, would leave an older manifest looking current. Paths hold no configuration values: a case's directory is named by its `case_id`.
- **`experiment.json`.** One for each plan, recording the declaration, the planned and retired cases, and an entry for every plan so far, with its hash, how it was approved, its reason, and what changed. So the current plan's `experiment.json` holds the whole plan history (R03-AC03). It records no outcome.
- **The lock.** An exclusive, non-blocking `flock` on `experiment.lock`, or `msvcrt.locking` on Windows, held from before any record is read or written until the command ends. The operating system releases it when the process ends, so a killed run leaves no stale lock. A file system that refuses locks fails with `storage.write_failed`. The lock belongs to the output directory, and there's no per-account lock, because 0.3.0 updates no shared account object: a ranking system named by name or ID is read, and a single formula, 0.1.0's specification states, changes nothing in the account. That last rests on documentation, not on a check of the account ([open questions](#open-questions)).
- **Running an experiment.** The steps for a new experiment and for a resumed one, how a resume checks the records, and which cases are due: a case with no attempt, or whose attempts all failed without being possibly charged. A resume also checks each file the latest manifest lists, so that a record missing from an incomplete copy fails the check, instead of making its case due again; the alternative, reading no manifest, can't tell a missing attempt from one never made.
- **The experiment manifest.** Each session's: the experiment, the current plan and how this run approved it, every file of the records, and the counts: the current plan's cases by outcome, which add up (R03-AC08), the retired cases, the attempts, and the requests and authentication calls against the budget.
- **The experiment's attempts.** A run authenticates once ([required behavior](#required-behavior), 3), so an attempt may send with a token an earlier attempt of the same run obtained. A 1.0.0 start record can't record that, so an experiment's start and attempt records are version 1.1.0, and a screen run's stay 1.0.0. Each names its session, its place in the session's order (`sequence`), and the attempt whose authentication gave its token (`authenticated_by`), so a resume can check that no token crossed from one run to another, or was used after a 401 or 403 dropped it. `sequence`, not the start time, orders a session's attempts, and with the session orders a case's attempts for the manifest's counts; the alternative, start times, misorders attempts when the clock moves backward between them, and the check would then reject a valid experiment. The list of [contracts and schema versions](#contracts-and-schema-versions) had kept the attempt record unchanged; this follows the settled required behavior instead, which is an [open question](#open-questions) for the owner.

**Left for R03-T04:** the option that repeats an `unknown` case, and whether a case whose failed attempt may have been charged needs it too, and how a repeated case's outcome is counted.

**Not yet specified, for R03-T05 to finish:** where an experiment's normalized tables go, and their `original_key` and `original_value` for a case; the JSON summary's keys for an experiment, whose 1.1.0 `ids` and `counts` hold one case's; and the test pairing of every criterion above.

R03-T03 also resolved the [open question](#open-questions) on new versions, as it recommended, and added six: the start and attempt records' versions, the revision's reason, approving a resumed plan again, failed cases on resume, stopping after an error every later case would get, and the per-account lock.

**The owner's confirmation.** On 2026-10-08, after R03-T03's pull request merged, the owner confirmed everything above, and the defaults of its six [open questions](#open-questions): start and attempt records 1.1.0 for an experiment; a reason required for every revision; each resume approving its plan again, by the same hash; a resume sending again only a failed case that wasn't possibly charged, which R03-T04 specified; a run that stops after Trial Folio's own authentication call fails, or after `provider.quota_exceeded`, which changes a settled failure row and R03-AC05, so it's recorded as [D-32](../spec.md#decisions), and which ends with `execution.partial`, exit 6, as a run the budget stops does; and no per-account lock in 0.3.0, which R03-T11's live check verifies by comparing the account's ranking systems before and after a formula-ranked run. R03-T05 builds on them as confirmed.

### What R03-T04 specified

On 2026-10-08, R03-T04 specified the option that repeats a case, in [repeating a case](../contracts.md#repeating-a-case), and answered what R03-T03 left for it:

- **Which cases a resume sends.** Each case of the plan is complete, with a succeeded attempt; due, when none of its attempts is possibly charged; or awaiting a repeat, when one is and none succeeded. A resume skips the first, sends the second, and sends the third only with `--repeat` ([the cases that are due](../contracts.md#running-an-experiment)). That's R03-T03's rule, stated by case, and it answers the [open question](#open-questions) on failed cases as R03-T03 recommended: a failed case whose request may have reached Portfolio123, such as one rejected with a 400, needs `--repeat`, as an `unknown` one does. The alternative, sending every failed case again, would send again, without asking, a request that may already have been charged. And if `--repeat` left such a case out, it could never be sent again, since a revision keeps a case whose settings didn't change, with its attempts.
- **The option.** `--repeat <case-key>`, once for each case, names a case of the plan the run approves, as the [open question](#open-questions) recommended. A repeat sends the case's request in a new attempt of the same case, in the plan's order and within the budget. A case that a revision kept can be repeated in the revision's run, under its key there.
- **The confirmation.** When stdin and stderr are terminals, and there's no `--approve`, the CLI lists each case to repeat with its latest attempt whose request may already have been charged, says that a repeat may be charged again and what budget it leaves, and asks the user to type `repeat`. With `--approve`, or without a terminal, the CLI never asks, as for approval, and the option is the confirmation: `--repeat <case-key>:<attempt-id>`, which names that attempt, as `--approve` names a plan's hash. The full plan display gives the exact option for each case awaiting a repeat, and so do the messages of a run that ends with one, and of a repeat that fails.
- **One confirmation, one repeat.** A confirmation names an attempt, and allows one send after it that may reach Portfolio123. Once a repeat may have reached Portfolio123, its confirmation is used, so the same command, run again after an interruption, doesn't repeat the case again: it says so, and resumes the rest. A repeat that sent nothing, such as one whose authentication failed, leaves its confirmation unused, and the same command tries it again. The alternative, a key with a flag that acknowledges the charge, such as `--accept-repeat-charge`, would repeat the case each time the same command ran, so a script that resumes an experiment by running its command again would pay again after each uncertain repeat.
- **`repeat_of`.** The start, attempt, and authentication records of an attempt that `--repeat` starts name the attempt its confirmation named, and `null` otherwise ([experiment attempts](../contracts.md#experiment-attempts)). A resume checks that each attempt sent after a possibly charged attempt of its case names the latest one, so the records show that no request that may have been charged was sent again without a confirmation. R03-T03 had specified these records, and nothing has built them yet.
- **Counting a repeated case.** A repeat is an attempt of the same case, so it's a provider operation in [METH-03.2](../methodology.md#meth-03-research-history-and-multiple-testing)'s terms, not a candidate. The [manifest](../contracts.md#the-experiment-manifest) counts the repeats apart from the other attempts, and counts a case by its latest possibly charged attempt. That refines R03-T03's rule, by the latest attempt, which would count an `unknown` case as `failed` after a repeat that sent nothing. Without a repeat, the two rules give the same outcome.
- **What fails.** These fail with `plan.approval_required`, exit 2, and send nothing, as a `--revision-reason` with no revision does: `--repeat` with a screen or a new experiment; a key that names no case of the plan, or names a due case; an attempt ID that names no possibly charged attempt of that case, or one that succeeded; and a repeat that isn't confirmed. A confirmation already used, and a key alone for a complete case, don't fail: the case isn't repeated, and the run resumes the rest, so the command that made a repeat, run again, resumes the experiment. A malformed value is a usage error from the parser.
- **Not offered.** Repeating a complete case, which would be a reproduction, and repeating a retired case.

**For R03-T05:** the JSON summary's keys for the cases awaiting a repeat, with the experiment's other keys; and the test pairing of the above, including a repeat whose authentication fails, a used confirmation, and the same command run again after an interrupted repeat.

**For R03-T10:** how the report shows each repeat and the attempt it repeated, and marks the cases awaiting one.

R03-T04 also resolved two [open questions](#open-questions), as recommended: how a repeat looks, and failed cases on resume. It added one: whether an acceptance criterion covers the repeat.

**The owner's confirmation.** On 2026-10-08, before R03-T04's pull request merged, the owner confirmed everything above, as recommended: the confirmation that names an attempt, and allows one repeat; `--repeat` for a failed case whose request may have reached Portfolio123; a case's outcome by its latest possibly charged attempt; `plan.approval_required` for a repeat that can't apply or isn't confirmed; and no repeat of a complete or retired case. They also added R03-AC14, which covers the repeat ([D-31](../spec.md#decisions)). R03-T05 builds on them as confirmed.

### What R03-T05 completed

On 2026-10-08, R03-T05 finished the specification:

- **Test pairing.** The [test pairing](#test-pairing) names a check, its fixtures, and its test doubles for each acceptance criterion. Experiment tests build the experiments they use during the test, with `trialfolio run` or the core, over the fake Portfolio123 server, and never commit them: their values are invented, but nothing labels them synthetic, so a committed copy would read as Portfolio123's backtests ([DSC-04](../disclaimers.md#dsc-04-actual-simulated-and-hypothetical-results)), as with 0.2.0's runs. The one committed experiment is synthetic, written through the core with the demo's client, as an [open question](#open-questions) recommends.
- **Verification commands.** [Verification commands](#verification-commands-and-expected-evidence) gives each command and its evidence. The live check runs two cases, 10 credits at the documented cost, checks that one authentication serves both, and resumes the experiment offline. The owner compares the account's ranking systems before and after it.
- **What R03-T03 and R03-T04 left for it,** in [contracts.md](../contracts.md):
  - **Normalized tables.** Each case with a result has a run's two tables in its own directory, labeled with its `case_id`, with `original_key` and `original_value` from the experiment configuration ([an experiment's normalized tables](../contracts.md#an-experiments-normalized-tables)). A resume writes those a stopped run didn't, and the manifest lists them, with each parser version that wrote them.
  - **The JSON summary.** Version 1.2.0, for every command, adds an experiment's `ids`, its `cases`, each with the attempt ID that confirms a repeat, and its counts ([JSON summary](../contracts.md#json-summary)).
  - **Progress and cancellation in the core,** which R03-AC13 checks: events that name cases by `case_id`, and a cancellation between attempts that ends the session as a spent budget does ([progress and cancellation](../contracts.md#running-an-experiment)).
  - **A synthetic experiment.** The core can execute an experiment with the demo's client, which no command does, and its manifest and report label it synthetic ([the experiment manifest](../contracts.md#the-experiment-manifest)). It's the historical experiment's source.
- **New acceptance criteria.** R03-AC15 to R03-AC19 cover behavior that contracts.md specifies, but no criterion covered: the logs, the JSON summary, the records check on resume, each case's tables, and storage failures and interrupts. Each of 0.1.0 and 0.2.0 has a criterion for each of these. Adding them changes the settled acceptance criteria, so the owner's sign-off decides them, and spec.md then records the decision.

## User outcome

Execute and review a controlled, finite experiment in which every planned case is accounted for ([OUT-03](../spec.md#users-and-outcomes)).

## Included scope

- `trialfolio run <config> --out <dir>` for a `kind: experiment` configuration, as for a screen ([D-24](../spec.md#decisions)). `run` chooses what to do by the configuration's `kind`, so it stays the one command that sends requests.
  - The configuration declares the experiment's purpose and one explicit baseline screen, as in 0.1.0.
  - It lists a small set of predefined variants, each changing verified settings only. Candidates are maximum holdings, rebalance frequency, a liquidity rule, slippage, and universe restrictions written as screen rules, such as a microcap cutoff, limited to types whose support 0.1.0 or 0.3.0 has verified.
  - Variants follow the default variant set ([P-13](../spec.md#proposed-defaults)) where the configuration doesn't list its own. Every variant value is one that [D-20](../spec.md#decisions) has verified. The universe isn't a variant: it's the baseline's, and another universe is a separate experiment ([D-19](../spec.md#decisions)).
  - It declares any prior research (see Required behavior).
- Compilation of all cases into fully resolved configurations before execution. Each case has a `case_key` and a `case_id`, and each attempt has an `attempt_id`.
- One approved plan covering every case and the whole request budget.
- Sequential execution, with progress saved after each case.
- Resume that skips verified completed cases, records uncertain completion separately, and never repeats a potentially charged request automatically.
- Plan revisions when the configuration changes.
- A lock that prevents two processes from running the same experiment, and per-account serialization of shared-state operations.
- An experiment report that shows every case and its outcome.

## Explicit exclusions

- Automatic search, adaptive variant generation, and optimization.
- Parallel or scheduled execution.
- Statistical acceptance decisions or ranking cases by "best".
- Variant types without recorded backend support.
- Descriptive return analytics, which is its own increment in the [roadmap](../roadmap.md#after-030).

## Supported inputs and examples

```text
trialfolio run study.yaml --out runs/study/
```

The configuration's keys, and two validated examples, are in [contracts.md](../contracts.md#experiment-configuration).

Running the same command against the same output directory resumes the experiment. After a change to the configuration, `--revision-reason <text>` and the approval of the revised plan revise it ([experiment plans and revisions](../contracts.md#experiment-plans-and-revisions)). A screen configuration still needs a new or empty output directory, as in 0.1.0.

A case whose request may have been charged, `unknown`, or `failed` after it may have reached Portfolio123, is sent again only when `--repeat` names it and the user confirms the possible repeat charge: on a terminal by typing `repeat`, and otherwise with the attempt's ID, as the plan display gives it ([repeating a case](../contracts.md#repeating-a-case)):

```text
trialfolio run study.yaml --out runs/study/ --repeat slippage-050
trialfolio run study.yaml --out runs/study/ --approve <plan-hash> --repeat slippage-050:<attempt-id>
```

## Required behavior

1. **Compile, then approve.** Resolve every case before any request. Show every case, its `case_id`, and the total budget. Require one approval of the plan hash for the whole experiment.
2. **Record research context.** Record the experiment's purpose, the planned cases, and any declared prior research, meaning earlier outcome-informed work on the same idea, including work done outside Trial Folio. Record it as the user supplied it, with the status complete, partial, or unknown. Trial Folio cannot verify it and says so.
3. **Execute sequentially.** Save each attempt atomically before starting the next case. Stop before exceeding the budget, which bounds both the requests and the authentication calls ([contracts.md, budget](../contracts.md#budget-and-retries)). Authenticate before the first request, and again only after a 401 or 403 ([contracts.md, HTTP exchanges](../contracts.md#http-exchanges)).
4. **Resume safely.** On restart, skip cases with a verified `succeeded` attempt. For any `running` attempt, which has a start record and no attempt record, write its attempt record without rewriting anything: `succeeded` if its response was saved, otherwise `unknown`, possibly charged ([contracts.md, uncertain completion](../contracts.md#uncertain-completion)).
   - Do not repeat `unknown` cases automatically. Repeating one requires an explicit user action that names the case and acknowledges a possible repeat charge. It creates a new attempt of the same case.
5. **Revise explicitly.** If the configuration changes, fail with `plan.changed` unless the user approves a plan revision.
   - The revision records its reason and the new hash.
   - A case whose resolved configuration changed gets a new `case_id`, and the old case and its attempts stay in the record.
   - A case whose resolved configuration did not change keeps its identity and completed attempts.
6. **Account for every case.** Planned cases = succeeded + failed + skipped + unknown + not yet run. The report and manifest show each count, and every case appears in the report.
7. **Keep execution separate from usefulness.** The report never orders or highlights cases by performance as a selection. Statistical validation and trading readiness read "Not assessed".

## Failure and incomplete-data behavior

| Situation | Behavior |
|---|---|
| A case fails | Recorded, and execution continues with the next case. The command ends with `execution.partial`, exit 6. |
| Trial Folio's own authentication call fails, or a request gets `provider.quota_exceeded` | Recorded, and no later case starts, as when the budget is spent, since every later case would end the same way ([D-32](../spec.md#decisions)). The command ends with `execution.partial`, exit 6, and a resume runs the cases not started. |
| Interrupted | Progress so far is durable. Rerunning resumes. |
| Uncertain completion | The case is `unknown`, reported separately, and not repeated automatically |
| Configuration changed since the plan | `plan.changed`, exit 3, unless a revision is approved |
| Another process holds the lock | `experiment.locked`, exit 4 |
| Budget would be exceeded | Stops before the request; the remaining cases stay not yet run |

## Required outputs

`manifest.json`, `experiment.json`, `plan.json` with its revisions, and `cases/<case_id>/attempts/<attempt_id>/` for every attempt. Also normalized CSVs covering all cases, `report.html`, and `logs/`. No file is ever replaced, so each plan's `plan.json` and `experiment.json` are in `plans/<n>/`, and each run's `report.html` and `manifest.json` in `sessions/<s>/`, as [experiment output](../contracts.md#experiment-output) lays them out. Each case's normalized CSVs are in `cases/<case_id>/normalized/`, once its attempt succeeds ([an experiment's normalized tables](../contracts.md#an-experiments-normalized-tables)). Also the [JSON summary](../contracts.md#json-summary), version 1.2.0, on stdout with `--json`.

**The live check** (`tests/live/test_experiment.py`). It refuses to start without credentials, or with a budget below the plan's `credits`. It runs only with the owner present, who grants the network access for its `trialfolio run` subprocess, as for [0.1.0's](0.1.0-api-execution.md#verification-commands-and-expected-evidence): the guard stays on, and lets that subprocess reach Portfolio123's API host as well as localhost.

1. **Before it,** the owner notes the account's ranking systems, in the Portfolio123 website.
2. **The run.** The experiment is `default-only.yaml`'s: the documented example's baseline, ranked by a formula, and the default variant, `rebalance-weeks-1`. Its two requests are those R01-T01 and R01-T05 verified, and its budget is 2 provider requests, 10 credits at the documented cost. It's approved with `--approve`, into a new directory under `reference/experiment-live-check/payloads/`. It exits 0, both cases succeed, and the attempt records show one `POST /auth`, before the first case, whose token the second case's request was sent with. No live call has checked that before: every live run so far sent one request, after its own authentication.
3. **The resume.** The test runs the same command again, under the full guard, with no network access. It resumes, makes no authentication call, sends nothing, and writes `sessions/2/`, with its report and manifest, and exits 0. So the experiment's records, written from Portfolio123's responses, are read and checked offline.
4. **After it,** the owner compares the account's ranking systems with the list from before. If one changed, a formula ranking updates a shared object, and 0.3.0 needs the per-account lock ([the lock](../contracts.md#the-lock)).

The committed run record, `reference/experiment-live-check/README.md`, gives the date, the versions, the credits used, the outcomes, and whether the ranking systems changed, and nothing from the responses or the account. The payloads stay git-ignored, and nothing from them leaves the folder.
