### What R04-T02 specified

On 2026-10-12, R04-T02 specified, in [contracts.md](../contracts.md), the [ranking definition](../contracts.md#ranking-definitions) and how it's read, [node paths](../contracts.md#node-paths), and [ranking variants](../contracts.md#ranking-variants), with a [validated example](../contracts.md#ranking-example), as screen configuration 1.1.0 and experiment configuration 1.1.0. By the owner's decision of the same day ([D-36](../spec.md#decisions)), it also specified [ranking snapshots](../contracts.md#ranking-snapshot-configuration), and that Trial Folio only reads the system a user selects.

- **The definition is a file** beside the configuration, named by `ranking.definition`, and copied byte for byte beside each plan's `configuration.yaml`, as `definition.xml`, as the open question's default proposed ([open questions](#open-questions)). A snapshot's directory, `ranking.snapshot`, is the other way to give one.
- **How it's read.** The file is UTF-8, without a byte-order mark, and each line end is read as a line feed, as XML reads them. So no carriage return is sent, and a checkout with Windows line endings gives the same case. The alternative was the file's bytes exactly, which would identify another case on another checkout.
- **Its form is the one R04-T01 read** in three saved systems, since Portfolio123 documents no schema for the XML:
  - one `RankingSystem` element, with no XML declaration, document type declaration, comment, or processing instruction;
  - nodes of three types only, `Composite`, `StockFormula`, and `StockFactor`;
  - on each node, a `Weight`: a decimal greater than 0, without a percent sign.

  A definition with another node type, a conditional node included, fails with `config.invalid` until a live check verifies it ([D-20](../spec.md#decisions)). The alternative was to accept other node types unread, which would send forms no check has seen.
- **Node paths.** A path names a node by the names from the top level down to it, separated by `/`, compared character for character, with `\/`, `\\`, and `\#` as escapes. A segment `#<n>` names a node by its position, which reaches a node without a name, such as R04-T01's `StockFactor` nodes, and one of two that share a name. Paths are written in quotes, and messages name them by their place in the file, never by their text, which holds the user's strategy definition.
- **Weight variants** give `set`: the weight of every node of one parent, the top level or a composite, summing to what the baseline's sum to. Only the weights that differ are rewritten, in the text between their attribute's quotes, and nothing else in the definition changes.
- **Removal variants** give `remove`, a `StockFormula` or `StockFactor` at any level, and `set`, the weights of the nodes left beside it, summing to what the parent's nodes summed to with it. Its element is taken out with its line. A composite isn't removed.
- **A case's identity.** A case's definition is hashed as an `artifact_id` is, and its resolved `ranking` holds that hash and its ranking method. So the `case_id` covers both, byte for byte, and not the definition's source, which the plan records. The plan holds each case's whole definition, in the request that writes it.
- **Ranking method, currency, and type.** `ranking_method` is required with a definition: `percentile_nas_negative` (2) or `percentile_nas_neutral` (4), the two values the [Rank API](https://portfolio123.customerly.help/en/articles/43323-api-rank) documents, both of which R04-T01 sent. A snapshot's is its system's. Currency and type are fixed, `USD` and `stock`, as every backtest's are, and a snapshot in another currency, or of another type, can't be a ranking. The alternative was to send a snapshot's currency, which no check has shown `rank_update` stores. This settles the currency, which the open question had left to R04-T02.
- **Ranking snapshots ([D-36](../spec.md#decisions)).** A `kind: ranking-snapshot` configuration names a saved system. `trialfolio run` shows a plan with one `rank_get`, at 1 credit, obtains the approval, and writes the system's XML as `definition.xml`, byte for byte, and `snapshot.json`, with the system's name, ID, ranking method, currency, type, and when it was read. A screen's or an experiment's `ranking.snapshot` names the directory. Reading it checks, offline, before the output directory is checked, that the snapshot is complete and can be a ranking.
- **Only `ApiRankingSystem` is written ([D-36](../spec.md#decisions)).** The exclusion's clause that would have allowed `rank_create`, or an `id`, if R04-T01 had shown the route needed one, is removed: R04-T01 showed it needs neither. R04-AC09 makes the rule a tested requirement.
- **`p123api`.** Version 3.1.0, the verified version, has `rank_get` and `rank_update`, and R04-T01 called both through it. So 0.4.0 keeps the wrapper, with no new ADR, as the owner decided on 2026-10-12.
- **A message's spelling.** Screen configuration 1.0.0's message for a ranking given as nodes or XML named `APIRankingSystem`. R04-T02 fixed it to `ApiRankingSystem`, the name R04-T01 found, in `src/trialfolio/contracts/screen_configuration.py`, with a test, as the owner decided on 2026-10-12.

**Checked against R04-T01's evidence.** Offline, the rules gave R04-T01's three verified variants, byte for byte, from saved system C's definition, and they read all eight definitions R04-T01 saved. The checks printed only counts and verdicts, so the definitions stay in R04-T01's git-ignored `payloads/` ([ranking variants](../contracts.md#ranking-variants)).

**Left for R04-T03:**

- **Each case's calls and their order.** The owner decided on 2026-10-12 that each backtest ranks by the name `ApiRankingSystem`, exactly as `rank_get` returns it. The alternative was its ID, which would cost a `rank_get` per experiment, and would change if the system were created again.
- **The plan** of a case that writes a definition, with a ranking variant's `variant` and the definition's source.
- **The records:** the start and attempt records of a case's `rank_update` and of a snapshot's `rank_get`, the snapshot's manifest, and the field shapes of the snapshot's plan and record.
- **The rows** `settings.csv` gives each node's weight, and what a review and the report show of them.
- **The budget's count** of each call, and the per-account lock.

**For R04-T04:** a test that repeats the example's validation; the invalid configurations its test pairing needs, one for each rule above; and, for R04-AC09, a test of every `rank_update` request's body.

**The owner's decisions.** On 2026-10-12, at R04-T02's pull request, the owner decided three of its rules, which change what the release had settled or the owner had confirmed, because R04-T01's evidence, or the release's own wording, contradicted it ([D-37](../spec.md#decisions), [open questions](#open-questions)):

- **The sum of a variant's weights** is the baseline's sum of the same nodes, which is 100 in every composite R04-T01 read, rather than 100, as the confirmed default said. R04-T01's step 4 kept the sum of top-level weights that don't sum to 100.
- **Nodes without a name** are named by their position, `#<n>`. The included scope named each node by its path of names, but `StockFactor` nodes have none.
- **A variant removes a factor,** never a composite. The included scope had offered "the removal of one node", and the open question's default a composite's removal too, while D-34 and the user outcome offer the removal of one factor, and R04-T01 verified only a factor's.

The owner also confirmed everything else above the same day, with the currency fixed at `USD`, and the definition file kept beside snapshots. R04-T03 builds on them as confirmed.

**Details from the review, confirmed by the owner on 2026-10-12.** The fixes after the first two reviews of R04-T02's pull request, on 2026-10-12, settled these rules in [contracts.md](../contracts.md), where the text had left them open or contradicted a rule it keeps. R04-T04's invalid configurations cover them too.

- **Each node once.** No two paths in a `set` name the same node, such as a name and its position: the node would get two weights, and the sum rule would count it twice. The rules had asked for every node of the parent, and no other, but not each once. The prototype already refused it ([ranking variants](../contracts.md#ranking-variants)).
- **A `set`'s paths are keys,** so every configuration's key rules apply to them: a path written twice fails, and so does one that holds a credential-like word, whose node is then named by its position. Every message about an entry names it by its place in the file, never by its path's text ([node paths](../contracts.md#node-paths)). The alternatives were to exempt a `set`'s keys from the credential check, which changes a rule every configuration has kept since 0.1.0, or to make `set` a list of paths and weights, which changes the form confirmed above.
- **A segment that starts with `#` is a position,** or it fails, so a mistyped position, such as `#01`, isn't read as a name; a name that starts with `#` is written `\#`. The alternative, which the prototype followed, was to read such a segment as a name, which then fails only as naming no node. Inside double quotes, YAML reads its own escapes first, so a path's `\` is written `\\` there.
- **A factor's elements.** A `StockFormula` holds no element but `Formula`, a `StockFactor` none but `Factor`, and those hold no element; Trial Folio doesn't read their text, or count them. It's the rule the prototype checked, which all eight of R04-T01's saved definitions passed. The alternative, exactly one `Formula` or `Factor`, would need a count from R04-T01's git-ignored definitions ([ranking definitions](../contracts.md#ranking-definitions)).
- **A file's source** is recorded in the plan by the definition's hash, not by the file's `artifact_id`, which line endings change, so a file's line endings don't change the plan hash, as [plan hashing](../contracts.md#plan-hashing) requires.
- **Copies come from the bytes read.** The copies of a definition file, and of a snapshot's `definition.xml` and `snapshot.json`, are written from the bytes read when the configuration is validated, as `configuration.yaml` is, never by reading the files again.

## User outcome

Test how a screen's results depend on its ranking system: run predefined variants that change the weights of its nodes, at the top level or within a composite, or remove one factor, as one finite experiment, with every case's ranking definition recorded ([OUT-03](../spec.md#users-and-outcomes)).

**The research task.** Reproducing published factor research builds the paper's factors as a Portfolio123 ranking system ([primary use](../spec.md#primary-use)). A reproduction then asks whether its result depends on the weights it chose, and on each factor: [METH-06.1](../methodology.md#meth-06-robustness-and-economic-usefulness) lists neighboring factor weights and the removal of one factor among the predefined perturbations, and [METH-09](../methodology.md#meth-09-reproducing-published-research) records how a reproduction departs from its source.

**The manual work it removes.** Today a researcher edits the weights in the website's ranking system editor, runs the screen again, and writes down each set of weights by hand. Release 0.3.0 can't vary the ranking at all: every case uses the baseline's. With 0.4.0, one configuration declares the ranking system and its variants, one approval covers them, and each case's records hold the exact definition it ran with.

## Included scope

- **A ranking system's definition as a ranking.** A screen configuration, and an experiment's baseline, may give the ranking as a ranking system's definition: the XML that Portfolio123's website shows in the Text Editor under Ranking System → Factors ([D-34](../spec.md#decisions)). Trial Folio reads it as a tree of nodes, each named by its path of node names, such as `Value/Earnings Yield`, with a node's position, such as `#2`, in place of a name it doesn't have ([D-37](../spec.md#decisions)).
- **Ranking variants.** An experiment's variants may change the baseline's ranking definition: the weights of the nodes of one parent, the top level or one composite, or the removal of one factor ([D-37](../spec.md#decisions)). Each is a case like any other: planned, approved, budgeted, and accounted for, as in [0.3.0](0.3.0-experiments.md).
- **Ranking snapshots.** A ranking system saved in the account can be the ranking through a snapshot of it. `trialfolio run` of a `kind: ranking-snapshot` configuration reads the system with one `rank_get`, under its own plan and approval, and saves its definition byte for byte, with a record of its source. A screen's or an experiment's ranking names the snapshot, and its plan records that source ([D-36](../spec.md#decisions)). The owner added this on 2026-10-12.
- **Sending a definition.** Each case writes its definition into `ApiRankingSystem` in the account, through Portfolio123's `rank_update`, then backtests the screen ranked by that system, in the sequence R04-T01 verifies. A per-account lock keeps two Trial Folio processes from interleaving those steps ([ADR 0001](../adrs/0001-python-and-portfolio123-integration.md)).
- **Records.** Each case's whole definition is in the plan, and its hash covers it. Each attempt records the definition it sent. `settings.csv` records each node's weight, so a review shows a changed weight as a declared change, and the report shows each case's weights.

## Explicit exclusions

- **Weight search, optimization, and generated grids.** Every variant is listed in the configuration, predefined and bounded ([METH-06.1](../methodology.md#meth-06-robustness-and-economic-usefulness)).
- **Other changes to a ranking system:** a node's formula, scope, rank direction, or type, an added node, the ranking method, and ETF ranking systems.
- **Writing any ranking system but `ApiRankingSystem`.** Trial Folio never updates, creates, or deletes another, so it never gives `rank_update` an `id`, and never calls `rank_create`: R04-T01 showed the route needs neither. It only reads one, with a snapshot's `rank_get` ([D-36](../spec.md#decisions)).
- **Reading a saved ranking system to build a plan.** The definition is in the configuration, or in a snapshot an earlier `run` read, so the plan is complete before anything is sent ([D-34](../spec.md#decisions), [D-36](../spec.md#decisions)). Only a snapshot's own run reads the account, under its own plan and approval.
- **Snapshots of ranks, each stock's rank on a date, which [METH-06.8](../methodology.md#meth-06-robustness-and-economic-usefulness) uses to diagnose signals; bucket performance; and comparisons of distinct ranking definitions as candidates,** which stay in the roadmap's [robustness and rank diagnostics](../roadmap.md#after-030) target. The ranking snapshots above, which save a ranking system's definition, aren't these.
- **Excluding other users of `ApiRankingSystem`.** The lock covers Trial Folio processes on one machine. It can't exclude the website, or another machine, using `ApiRankingSystem` at the same time, and the plan says so.
- **Parallel or scheduled execution,** as in 0.3.0.

## Supported inputs and examples

As R04-T02 specified them. The [ranking example](../contracts.md#ranking-example) gives the definition these paths name, and the whole experiment:

```yaml
baseline:
  # ...the screen's other settings, as in 0.3.0
  ranking:
    definition: 'ranking/value-momentum.xml'     # the XML from the website's Text Editor
    ranking_method: percentile_nas_negative      # or, instead of both: snapshot: 'ranking/value-momentum/'
variants:
  ranking:
    - key: value-heavy
      set: {'Value': 60, 'Momentum': 20, 'Quality': 20}            # top-level nodes
    - key: tilt-earnings-yield
      set: {'Value/Earnings Yield': 70, 'Value/Sales Yield': 30}   # within a composite
    - key: no-sales-yield
      remove: 'Value/Sales Yield'                                  # a factor's removal,
      set: {'Value/Earnings Yield': 100}                           # with the weights left
```

```yaml
kind: ranking-snapshot
schema_version: 1.0.0
system: 'Value and momentum'
```

## Required behavior

1. **The definition is the configuration's,** given in a file, or in a snapshot an earlier run read ([D-36](../spec.md#decisions)). The plan holds every case's whole definition, and its hash covers it. Nothing is read from the account to build a plan, so it's reviewed offline, without credentials, as in 0.3.0.
2. **Every weight is explicit.** A weight variant gives each weight it changes. A weight is never 0, which Portfolio123 reads as equal weighting ([ranking definitions](https://portfolio123.customerly.help/en/articles/13793-dataminer-ranking-definition)). Removing a factor removes its node.
3. **Each case writes its definition, then backtests.** A case's attempt writes its definition into `ApiRankingSystem` with `rank_update`, then backtests ranked by that system, in the sequence R04-T01 verifies, with any step it shows is needed, such as flushing cached ranks. Each call is a provider request that may be charged: it's recorded as an exchange, and counted against the budget.
4. **Only `ApiRankingSystem` changes.** The plan says that the run overwrites it in the account. A per-account lock keeps two Trial Folio processes from interleaving a case's write and backtest.
5. **Each case's definition is recorded.** The attempt's records hold the definition it sent, byte for byte. `settings.csv` has a row for each node's weight. A review shows a changed weight as a declared change, and the report shows each case's weights, without ranking the cases.
6. **Everything 0.3.0 requires of an experiment still holds:** resume, repeats, revisions, the budget, and accounting for every case.
7. **A snapshot only reads.** A snapshot's run reads the system its configuration names with one `rank_get`, under its own plan and approval, and saves the system's definition, byte for byte, with its source. The system a user selects is never written: Trial Folio writes only `ApiRankingSystem` ([D-36](../spec.md#decisions)).

## Failure and incomplete-data behavior

| Situation | Behavior |
|---|---|
| The configuration's definition is invalid: it isn't a ranking system's XML, a path names no node or more than one, a weight is 0, or a removal leaves a composite empty | `config.invalid`, exit 3, before anything is sent |
| `rank_update` is rejected | The case fails, and may have been charged. Its backtest isn't sent. |
| Interrupted between a case's write and its backtest | As in 0.3.0. `ApiRankingSystem` keeps the definition last written, and every case writes its own before its backtest. |
| Another Trial Folio process holds the account lock | Fails before sending anything, with an error R04-T03 specifies |
| A definition's file, or a snapshot's directory, doesn't exist | `input.not_found`, exit 3, before anything is sent |
| A snapshot isn't complete | `input.not_a_run`, exit 3, before anything is sent |
| A snapshot's definition, ranking method, currency, or type can't be a ranking | `config.invalid`, exit 3, before anything is sent |
| A snapshot's `rank_get` fails, or its response lacks the system's fields | As a screen run's failed request. The snapshot has no definition, and its manifest's outcome is `failed`. |

## Required outputs

0.3.0's, with each case's definition in its plan and its records, and each node's weight in its `settings.csv`, as R04-T03 specifies. Beside each plan's `configuration.yaml`, in a screen run's directory or an experiment plan's `plans/<n>/`, a ranking given as a definition or a snapshot adds `definition.xml`, a copy of the definition file or of the snapshot's, and a snapshot also adds its `snapshot.json` ([ranking definitions](../contracts.md#ranking-definitions)). A ranking snapshot's run writes a directory of its own: `plan.json`, `configuration.yaml`, its attempt, `definition.xml`, `snapshot.json`, `manifest.json`, and `logs/` ([ranking snapshot output](../contracts.md#ranking-snapshot-output)).

## Acceptance criteria

R04-T04 pairs each with a check, and may add criteria with the owner's decision.

| ID | Criterion |
|---|---|
| R04-AC01 | Every case's whole ranking definition, and each node's weight, is shown in the plan, with the case's `case_id`, before any request, and the plan hash covers it |
| R04-AC02 | A definition that isn't a ranking system's XML, a path that names no node or more than one, a weight of 0, and a removal that leaves a composite empty each fail with `config.invalid`, and nothing is sent |
| R04-AC03 | Each case is sent in R04-T01's verified sequence: its definition written into `ApiRankingSystem`, then the backtest ranked by that system. Its records hold the definition it sent, byte for byte. |
| R04-AC04 | `settings.csv` holds each case's node weights, and a review of two cases shows a changed weight as a declared change |
| R04-AC05 | Two Trial Folio processes using one account never interleave a case's write and its backtest |
| R04-AC06 | The report shows each case's weights, and orders, ranks, and marks no case by a value |
| R04-AC07 | A recorded opt-in live check runs a small weight experiment with the owner's credentials and a declared budget: a changed weight changes a metric, and a later run with the baseline's definition, such as a screen run, restores the baseline case's metrics. The budget covers both runs, and the owner confirms that no ranking system but `ApiRankingSystem` changed. |
| R04-AC08 | A ranking snapshot reads the system its configuration names with one `rank_get`, under its own approved plan, and writes nothing to the account. It saves the system's XML byte for byte, with its name, ID, ranking method, currency, type, and when it was read. A screen or experiment whose ranking names the snapshot builds its plan offline, without credentials, and the plan records the definition's source. The owner added it on 2026-10-12 ([D-36](../spec.md#decisions)). |
| R04-AC09 | Trial Folio writes only `ApiRankingSystem`: no `rank_update` request carries an `id`, Trial Folio calls no other operation that writes a ranking system, and the system a snapshot reads is only read. A test checks the body of every `rank_update` request. The owner added it on 2026-10-12 ([D-36](../spec.md#decisions)). |
