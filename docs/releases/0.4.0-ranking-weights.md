## User outcome

Test how a screen's results depend on its ranking system: run predefined variants that change the weights of its nodes, at the top level or within a composite, or remove one factor, as one finite experiment, with every case's ranking definition recorded ([OUT-03](../spec.md#users-and-outcomes)).

**The research task.** Reproducing published factor research builds the paper's factors as a Portfolio123 ranking system ([primary use](../spec.md#primary-use)). A reproduction then asks whether its result depends on the weights it chose, and on each factor: [METH-06.1](../methodology.md#meth-06-robustness-and-economic-usefulness) lists neighboring factor weights and the removal of one factor among the predefined perturbations, and [METH-09](../methodology.md#meth-09-reproducing-published-research) records how a reproduction departs from its source.

**The manual work it removes.** Today a researcher edits the weights in the website's ranking system editor, runs the screen again, and writes down each set of weights by hand. Release 0.3.0 can't vary the ranking at all: every case uses the baseline's. With 0.4.0, one configuration declares the ranking system and its variants, one approval covers them, and each case's records hold the exact definition it ran with.

## Included scope

- **A ranking system's definition as a ranking.** A screen configuration, and an experiment's baseline, may give the ranking as a ranking system's definition: the XML that Portfolio123's website shows in the Text Editor under Ranking System → Factors ([D-34](../spec.md#decisions)). Trial Folio reads it as a tree of nodes, each named by its path of node names, such as `Value/Earnings Yield`.
- **Ranking variants.** An experiment's variants may change the baseline's ranking definition: the weights of the children of one composite, or the removal of one node. Each is a case like any other: planned, approved, budgeted, and accounted for, as in [0.3.0](0.3.0-experiments.md).
- **Sending a definition.** Each case writes its definition into `ApiRankingSystem` in the account, through Portfolio123's `rank_update`, then backtests the screen ranked by that system, in the sequence R04-T01 verifies. A per-account lock keeps two Trial Folio processes from interleaving those steps ([ADR 0001](../adrs/0001-python-and-portfolio123-integration.md)).
- **Records.** Each case's whole definition is in the plan, and its hash covers it. Each attempt records the definition it sent. `settings.csv` records each node's weight, so a review shows a changed weight as a declared change, and the report shows each case's weights.

## Explicit exclusions

- **Weight search, optimization, and generated grids.** Every variant is listed in the configuration, predefined and bounded ([METH-06.1](../methodology.md#meth-06-robustness-and-economic-usefulness)).
- **Other changes to a ranking system:** a node's formula, scope, rank direction, or type, an added node, the ranking method, and ETF ranking systems.
- **Any ranking system but `ApiRankingSystem`.** Trial Folio never updates, creates, or deletes another, so it never gives `rank_update` an `id`, and never calls `rank_create`, unless R04-T01 shows the route needs it and the owner decides so.
- **Reading a saved ranking system to build a plan.** The definition is in the configuration, so the plan is complete before anything is sent ([D-34](../spec.md#decisions)).
- **Rank snapshots, bucket performance, and comparisons of distinct ranking definitions as candidates,** which stay in the roadmap's [robustness and rank diagnostics](../roadmap.md#after-030) target.
- **Excluding other users of `ApiRankingSystem`.** The lock covers Trial Folio processes on one machine. It can't exclude the website, or another machine, using `ApiRankingSystem` at the same time, and the plan says so.
- **Parallel or scheduled execution,** as in 0.3.0.

## Supported inputs and examples

The intended shape, which R04-T02 specifies and may change:

```yaml
baseline:
  # ...the screen's other settings, as in 0.3.0
  ranking:
    system: 'ranking/core-combo.xml'          # the XML from the website's Text Editor
variants:
  ranking:
    - key: value-heavy
      set: {'Value': 50, 'Momentum': 25, 'Quality': 25}            # top-level nodes
    - key: tilt-earnings-yield
      set: {'Value/Earnings Yield': 60, 'Value/Sales Yield': 40}   # within a composite
    - key: no-sales-yield
      remove: 'Value/Sales Yield'                                  # factor removal,
      set: {'Value/Earnings Yield': 100}                           # with the weights left
```

## Required behavior

1. **The definition is the configuration's.** The plan holds every case's whole definition, and its hash covers it. Nothing is read from the account to build a plan, so it's reviewed offline, without credentials, as in 0.3.0.
2. **Every weight is explicit.** A weight variant gives each weight it changes. A weight is never 0, which Portfolio123 reads as equal weighting ([ranking definitions](https://portfolio123.customerly.help/en/articles/13793-dataminer-ranking-definition)). Removing a factor removes its node.
3. **Each case writes its definition, then backtests.** A case's attempt writes its definition into `ApiRankingSystem` with `rank_update`, then backtests ranked by that system, in the sequence R04-T01 verifies, with any step it shows is needed, such as flushing cached ranks. Each call is a provider request that may be charged: it's recorded as an exchange, and counted against the budget.
4. **Only `ApiRankingSystem` changes.** The plan says that the run overwrites it in the account. A per-account lock keeps two Trial Folio processes from interleaving a case's write and backtest.
5. **Each case's definition is recorded.** The attempt's records hold the definition it sent, byte for byte. `settings.csv` has a row for each node's weight. A review shows a changed weight as a declared change, and the report shows each case's weights, without ranking the cases.
6. **Everything 0.3.0 requires of an experiment still holds:** resume, repeats, revisions, the budget, and accounting for every case.

## Failure and incomplete-data behavior

| Situation | Behavior |
|---|---|
| The configuration's definition is invalid: it isn't a ranking system's XML, a path names no node or more than one, a weight is 0, or a removal leaves a composite empty | `config.invalid`, exit 3, before anything is sent |
| `rank_update` is rejected | The case fails, and may have been charged. Its backtest isn't sent. |
| Interrupted between a case's write and its backtest | As in 0.3.0. `ApiRankingSystem` keeps the definition last written, and every case writes its own before its backtest. |
| Another Trial Folio process holds the account lock | Fails before sending anything, with an error R04-T03 specifies |

## Required outputs

0.3.0's, with each case's definition in its plan and its records, and each node's weight in its `settings.csv`, as R04-T03 specifies.

## Acceptance criteria

R04-T04 pairs each with a check, and may add criteria with the owner's decision.

| ID | Criterion |
|---|---|
| R04-AC01 | Every case's whole ranking definition, and each node's weight, is shown in the plan, with the case's `case_id`, before any request, and the plan hash covers it |
| R04-AC02 | A definition that isn't a ranking system's XML, a path that names no node or more than one, a weight of 0, and a removal that leaves a composite empty each fail with `config.invalid`, and nothing is sent |
| R04-AC03 | Each case is sent in R04-T01's verified sequence: its definition written into `ApiRankingSystem`, then the backtest ranked by that system. Its records hold the definition it sent, byte for byte. |
| R04-AC04 | `settings.csv` holds each case's node weights, and a review of two cases shows a changed weight as a declared change |
| R04-AC05 | Two Trial Folio processes using one account never interleave a case's write and its backtest |
| R04-AC06 | The report shows each case's weights, and orders, ranks, and marks no case by a value |
| R04-AC07 | A recorded opt-in live check runs a small weight experiment with the owner's credentials and a declared budget: a changed weight changes a metric, restoring it restores the baseline's metrics, and the owner confirms that no ranking system but `ApiRankingSystem` changed |

## Open questions

| Question | Impact | Recommended default | Resolve by |
|---|---|---|---|
| Does a backtest ranked by `ApiRankingSystem` use the definition just written, or ranks cached from an earlier one? Portfolio123 documents `rank_touch`, which "forces a flush of all cached ranks". | Whether the route works | Check it in R04-T01, step 5. If ranks are cached, add `rank_touch`, which takes the ID step 2 records, before each backtest, at 1 credit, once a further check the owner approves shows it works. Otherwise, the owner decides between that and `rank_create`, which leaves a ranking system in the account for each case, since the API documents no delete. | R04-T01 |
| What's the system's exact name? The Rank API documentation writes `ApiRankingSystem`, and the ranking-definition article `APIRankingSystem`. | Whether a backtest by name finds it | Use the name the owner reads in the website after R04-T01's first `rank_update`, which `rank_get` confirms before any backtest, in step 2 | R04-T01 |
| Does `rank_get` return exactly the XML `rank_update` sent? | Whether a case records what was stored, or only what was sent | Check it in R04-T01, step 2. If it does, each case records the definition it sent, and reads nothing back. Otherwise each case reads it back, at 1 credit. | R04-T01 |
| What ranking method, and currency, does a case rank with? `rank_get` returns them apart from the XML, and `rank_create` takes them as arguments of their own. | Whether a case ranks with what its plan shows, or with whatever `ApiRankingSystem` held before | The configuration gives the ranking method beside the definition, and the plan and `settings.csv` record it. Each `rank_update` sends it, if R04-T01 shows the call takes it; otherwise each case reads it back with `rank_get`, at 1 credit, and records it. | What does Portfolio123 require of a composite's weights: must they sum to 100, and does it rescale them? | Whether a variant must give every sibling's weight | A weight variant gives the weight of every child of the composite it changes, and a removal variant the weight of every node left in the composite it removes from. Either way they sum to 100, so no result depends on how Portfolio123 rescales. | R04-T02 |
| Is the definition read from a file beside the configuration, or written in it? | How a configuration holds a long definition | A file, named by a path relative to the configuration, and copied byte for byte into each plan's directory, as the configuration is | R04-T02 |
| Which nodes may a variant change? | Scope | The weight of any node; the removal of a formula node or a composite. A conditional node's branches aren't varied. | R04-T02 |
| What does a screen run record of its definition, and which of its contracts change, such as plan 1.0.0 and its start and attempt records? | Which versions a screen run with a definition writes | What an experiment's case records, in the same form, as a run's one case, in new versions of the contracts that change | R04-T03 |
| How does the budget count a case's calls? | The budget's meaning, and the plan's credits | `provider_requests` counts every provider request, of each kind, and the plan shows the credits at each request's documented cost: 1 for `rank_update` and 5 for a backtest | R04-T03 |
| Where is the per-account lock? | Which runs it serializes | A lock file in a directory every user of the machine can write, held from each case's write until its backtest ends, so it serializes every Trial Folio process on the machine, whichever OS user runs it, as R04-AC05 requires. A lock in the per-user state directory would serialize only one user's processes, which narrows R04-AC05. | R04-T03 |
