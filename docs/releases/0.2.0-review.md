### What R02-T01 confirmed

On 2026-10-05, R02-T01 checked the names in contracts.md against 0.1.0's code, and they agree:

- **Settings.** The 23 [screen settings](../contracts.md#screen-settings) have the same names, categories, declarable marks, and units, in the same order, as `SCREEN_SETTINGS` in `src/trialfolio/contracts/screen_settings.py`.
- **Declarable settings.** Twelve are marked declarable: `universe`, `rules`, `ranking`, `max_holdings`, `benchmark`, `start_date`, `end_date`, `rebalance_weeks`, `transaction_price`, `slippage_percent`, `pit_method`, and `precision`. The review configuration's `intended_changes` accepts exactly these, and `DECLARABLE_SETTINGS` in the same module holds the same 12, for R02-T04's model. Any other name, including a setting that isn't declarable, is `config.invalid`.
- **Metrics.** The 20 metrics of [`p123api-screen-backtest` version 1](../contracts.md#p123api-screen-backtest-version-1) have the same identifiers, subjects, and units, in the same order, as `METRICS` in `src/trialfolio/normalization.py`. Both mark the same four as benchmark-relative: `correlation`, `r_squared`, `beta`, and `alpha`.

It also made these changes:

- **What declarable means.** The screen settings said a declarable setting is one "a screen configuration can set to different values". Three of the 12, `transaction_price`, `pit_method`, and `precision`, take only one value in screen configuration 1.0.0, so that didn't match the table or the code. It now says what they mark: the value comes from a screen configuration key and is sent in the request. No setting's mark changed. A change declared to one of those three is `same`, flagged `intended_change_not_observed`, until a release verifies more of its values.
- **The rows of `differences.csv`.** [Differences between screen runs](../contracts.md#differences-between-screen-runs) uses these names: the labels, the 23 setting rows and the 20 metric rows in order, when two settings are the same, and when each metric is differenced, with its unit, its decimals, and how the difference is written. Each choice the earlier contracts left open is in the [open questions](#open-questions), with a recommended default.
- **`differences.csv`'s columns.** `difference_unit` and `difference_decimals` cover dates and counts, `reason` adds `unknown_period`, and `declared_reason` is given for every declared change, including one that wasn't observed.

### What R02-T02 specified

On 2026-10-05, R02-T02 specified the review's output in [contracts.md, review output](../contracts.md#review-output):

- **The layout.** `configuration.yaml`, the review configuration byte for byte, claims the output directory. `inputs/<label>/` holds each run's `manifest.json`, `plan.json`, and normalized tables, byte for byte, at their paths in the run, so the copies can be checked against the copied manifest. Then come `normalized/differences.csv`, `report.html`, and `manifest.json`, last.
- **What isn't copied.** The run's configuration, its start and attempt records, its request, its response, and its report. The copied manifest records each one's hash.
- **How it's written.** The review reads and checks each run once, and writes each copy from the bytes it checked. It checks the inputs before the output directory, as `trialfolio report` does.
- **The review manifest.** It records the `review_id`, the `baseline`, and `results`, which say what run each label names: the `artifact_id` of the run's manifest, whether the run is synthetic, its `plan_hash` and `case_id`, whether it has tables, and its response's `artifact_id`. Each copy's entry gives its label. The manifest records the differencing rules as a method with a version, `screen-run-differences` version 1, and counts `differences.csv`'s rows by classification. It has no plan hash, approval, parsers, or reproducibility, which the copied run manifests hold.
- **Labels.** A label names a directory, so the review configuration rejects the device names Windows reserves, such as `con` and `nul`.

The layout follows the recommended defaults of three open questions, which R02-T03 asks the owner to confirm: a review copies no responses; it copies every run's `plan.json`, which a run without tables needs; and it marks each synthetic result. [Included scope](#included-scope) and [required behavior](#required-behavior) name only the manifest and the tables; they'll name the plan too if the owner confirms copying it. R02-T02 also added three open questions: whether the configuration is copied with its `run` paths, which rows of `differences.csv` carry `identical_source`, and the code for a `run` directory that doesn't exist.

## User outcome

Compare saved runs against an explicit baseline, and see exactly what differs ([OUT-02](../spec.md#users-and-outcomes)).

## Included scope

- **`trialfolio review <config> --out <dir>`.** An offline comparison of two or more saved Trial Folio runs against an explicit baseline, named in a [review configuration](../contracts.md#review-configuration).
- **A self-contained review.** Each compared run's manifest and normalized tables are copied into the review output, byte for byte, so the review stands on its own.
- **Settings comparison.** Settings are compared as intended changes or unexplained mismatches, and critical categories are flagged. The settings are Trial Folio's own records of what it sent, so they're `verified`.
- **Metric comparison.** Differences are computed only between comparable values, with explicit units.
- **Outputs:** `differences.csv`, a manifest, a self-contained, script-free HTML report, and the [JSON summary](../contracts.md#json-summary).

## Explicit exclusions

- **Outside results.** Results not produced by Trial Folio, including DataMiner or website exports ([ADR 0005](../adrs/0005-build-on-the-portfolio123-api-only.md)).
- **Network access and provider requests.**
- **Analysis.** Charts, statistical comparison, and any ranking of runs by performance.
- **Assessments.** Statistical validation and trading readiness are reported as "Not assessed".

## Required behavior

1. **Validate before writing.** Validate the configuration, and confirm that every input is a complete Trial Folio run: its manifest is present, and the files it lists match their hashes. Nothing is written until every input passes.
2. **Copy the inputs.** Copy each run's manifest and normalized tables into the review output, byte for byte, and record their hashes.
3. **Compare settings.**
   - Classify every setting as `same`, `intended_change`, `unexplained_mismatch`, or `unknown`. The settings are the 23 [screen settings](../contracts.md#screen-settings), and [differences between screen runs](../contracts.md#differences-between-screen-runs) says when two are the same.
   - Flag `unexplained_mismatch` and `unknown` in critical categories, including the data source.
   - Flag a declared change that isn't present with `intended_change_not_observed`.
4. **Compare metrics.**
   - Compute differences only between comparable values. Percent-to-percent differences are in percentage points. [Differences between screen runs](../contracts.md#differences-between-screen-runs) gives each metric's rule.
   - Show benchmark-relative metrics side by side without a difference when the benchmarks differ.
   - Never exceed the source precision.
5. **Keep missing values explicit.** An unavailable value stays unavailable, with its reason, and is never zero.
6. **Render the report** following [contracts.md, reports](../contracts.md#reports). Statistical validation and trading readiness read "Not assessed".
7. **Run offline.** Make no network access. Require the [license acknowledgment](../contracts.md#license-acknowledgment), and log as [contracts.md, logging](../contracts.md#logging-and-local-diagnostics) specifies: under `<out>/logs/` once the output directory is claimed.

## Failure and incomplete-data behavior

| Situation | Behavior |
|---|---|
| An input is not a complete run, or its files don't match their manifest hashes | `input.not_a_run`, exit 3. The message names the input and the problem. Nothing is written. |
| An input's schema version has no reader | `artifact.unknown_schema_version`, exit 3; nothing is written |
| Misspelled key, duplicate key, intended change on the baseline, or unknown setting name | `config.invalid`, exit 3; nothing is written |
| Two results point to runs with byte-identical responses | Warning, flagged `identical_source` |
| Output directory exists and isn't empty | `output.not_empty`, exit 4; nothing is modified |
| No license acknowledgment | `license.not_acknowledged`, exit 2 |

## Required outputs

This is the review layout R02-T02 specified. [contracts.md, review output](../contracts.md#review-output) shows it as a tree, and says how each file is written:

- `manifest.json`, the review manifest
- `configuration.yaml`, the byte-for-byte copy of the review configuration
- `inputs/<label>/` for each result, holding byte-for-byte copies of its run's `manifest.json`, `plan.json`, and, when the run has them, `normalized/metrics.csv` and `normalized/settings.csv`
- `normalized/differences.csv`
- `report.html`
- `logs/`

Also the [JSON summary](../contracts.md#json-summary) on stdout with `--json`.

## Acceptance criteria

| ID | Criterion |
|---|---|
| R02-AC01 | A two-run review writes the manifest, `differences.csv`, and the report, and exits 0 |
| R02-AC02 | Copied inputs are byte-identical to the runs' files, and the manifest's hashes match |

## Open questions

| Question | Impact | Recommended default | Resolve by |
|---|---|---|---|
| Should a review accept runs written by different Trial Folio versions? | Compatibility | Yes, when each run's schema version has a reader | R02-T03 |
| Should a review copy full responses, or only manifests and normalized tables? | Output size, self-containment, and what a shared review holds | Neither the response nor the request. The review copies each run's manifest, plan, and normalized tables ([review output](../contracts.md#review-output)). The copied manifest records each file's hash, the response's included, and the review manifest's `results` record each response's, which is all `identical_source` needs. A response holds Portfolio123's data, including per-period series a review doesn't compare, and a review may be shared ([D-14](../spec.md#decisions)). | R02-T03 |
| Can a review include a run without normalized tables, because its attempt didn't succeed or its response was invalid? | Whether failed runs, which INV-01 keeps, can be compared | Yes. Its settings are compared from its plan, as its own report shows them. The review copies every run's `plan.json`, which also holds the run's title and purpose and its wrapper's versions ([review output](../contracts.md#review-output)). Its plan's rows stand in for `settings.csv`'s, with the plan's flags ([differences between screen runs](../contracts.md#differences-between-screen-runs)). Every metric is `unavailable`, with `input_unavailable`, and the report says why the run has no tables, from its copied manifest's `error`. The alternative is to copy `plan.json` only for a run without tables. | R02-T03 |
| Can a review include the run `trialfolio demo` writes? | Synthetic values must never read as Portfolio123's ([DSC-04](../disclaimers.md#dsc-04-actual-simulated-and-hypothetical-results)) | Yes, alone or with real runs. The review manifest marks each synthetic result in `results`, and is `synthetic` when any result is ([review output](../contracts.md#review-output)). The report labels each synthetic result, as the demo's own report does, and when any is synthetic, says which before any result, so no difference reads as Portfolio123's. | R02-T03 |
| Are the benchmark's own metrics differenced when the runs' benchmarks differ? | Whether the gap between two different benchmarks' returns reads as a change | No. Rows 15–20 are differenced only when the runs' `benchmark` settings are the same, and are otherwise `not_comparable`, with `different_benchmark` ([differences between screen runs](../contracts.md#differences-between-screen-runs)). | R02-T03 |
| How are the coverage rows compared? | Whether a review shows how far coverage moved | Coverage is the period, so the period rule doesn't apply to it. Dates are differenced in `days`, and `coverage_periods` in `count`, both with 0 decimal places. | R02-T03 |
| What reason does a metric get when a run's period is unknown? | An unknown period isn't a different one | A new reason, `unknown_period` | R02-T03 |
| Which reason is given when several apply? | `reason` holds one code | The first of `different_unit`, `different_benchmark`, and `different_period` or `unknown_period`. The setting rows show every difference. | R02-T03 |
| How is a difference rounded to the smaller decimal count, and how is it written? | The same inputs must always give the same `differences.csv` | Half to even, the default of Python's `decimal`, which doesn't lean either way. The count is the values' recorded `source_decimals`. Saving drops trailing zeros, so `12.5` has one decimal place even when it was requested at 4, but a whole number saved as a float keeps its `.0`, so `12.0` has one too. A difference is written with exactly that many decimal places, as `0.10`, so its digits match `difference_decimals`, and a zero difference is written without a sign, never `-0.0` ([differences between screen runs](../contracts.md#differences-between-screen-runs)). | R02-T03 |
| Which flags does a setting row carry, and which set `flagged`? | Whether `flagged` stays a signal or turns into noise | A row carries the flags either run's `settings.csv` row has, or its plan's row for a run without tables, and its comparison's own. `flagged` is true for `critical_unexplained_mismatch`, `critical_unknown`, `intended_change_not_observed`, `coverage_mismatch`, `unsupported_value`, and `identical_source`. `not_snapshotted` and `inferred_default` don't set it. Every screen run's `universe` row is `not_snapshotted`, and its `data_vendor` and `risk_stats_period` rows are `inferred_default`, so those would flag every review. A `ranking` row is `not_snapshotted` only for a ranking system named or given by ID, and isn't flagged either: a ranking system edited between two runs doesn't show as a change, just as a universe edited between them doesn't. The report lists each external reference instead. The alternative is to have `not_snapshotted` set `flagged` on the `ranking` row only. | R02-T03 |
| Should a review copy its configuration byte for byte, though its `run` paths can name the user? | Whether a shared review shows where the user keeps runs ([D-14](../spec.md#decisions)) | Yes. It's the source of the baseline, the labels, and each declared change's reason ([INV-04](../spec.md#enduring-invariants)). The manifest and the report never repeat the paths, and the user guide will recommend paths relative to the configuration. The alternative is to record the configuration's parsed content without its paths, which loses the source's bytes. | R02-T03 |
| Which rows of `differences.csv` carry `identical_source`? | Where a reader of the table learns that two results have one response | Every metric row of a result whose saved response is byte-identical to the baseline's. Identical responses give identical metrics, so the flag says that the zero differences come from one response, not from two runs that agree. `differences.csv` compares each result only with the baseline, so two other results with identical responses show only in the review manifest's `results`, and in the report, which names both. | R02-T03 |
| Is a `run` directory that doesn't exist `input.not_found` or `input.not_a_run`? | Whether `review` and `trialfolio report` give the same code for the same problem | `input.not_found`, exit 3, as `trialfolio report` gives ([running the commands](../contracts.md#cli-behavior)). The message names the result's label. The failure table and R02-AC06 then name it too. | R02-T03 |
