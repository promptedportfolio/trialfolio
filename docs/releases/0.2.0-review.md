### What R02-T01 confirmed

On 2026-10-05, R02-T01 checked the names in contracts.md against 0.1.0's code, and they agree:

- **Settings.** The 23 [screen settings](../contracts.md#screen-settings) have the same names, categories, declarable marks, and units, in the same order, as `SCREEN_SETTINGS` in `src/trialfolio/contracts/screen_settings.py`.
- **Declarable settings.** Twelve are marked declarable: `universe`, `rules`, `ranking`, `max_holdings`, `benchmark`, `start_date`, `end_date`, `rebalance_weeks`, `transaction_price`, `slippage_percent`, `pit_method`, and `precision`. The review configuration's `intended_changes` accepts exactly these, and `DECLARABLE_SETTINGS` in the same module holds the same 12, for R02-T04's model. Any other name, including a setting that isn't declarable, is `config.invalid`.
- **Metrics.** The 20 metrics of [`p123api-screen-backtest` version 1](../contracts.md#p123api-screen-backtest-version-1) have the same identifiers, subjects, and units, in the same order, as `METRICS` in `src/trialfolio/normalization.py`. Both mark the same four as benchmark-relative: `correlation`, `r_squared`, `beta`, and `alpha`.

It also made these changes:

- **What declarable means.** The screen settings said a declarable setting is one "a screen configuration can set to different values". Three of the 12, `transaction_price`, `pit_method`, and `precision`, take only one value in screen configuration 1.0.0, so that didn't match the table or the code. It now says what they mark: the value comes from a screen configuration key and is sent in the request. No setting's mark changed. A change declared to one of those three is `same`, flagged `intended_change_not_observed`, until a release verifies more of its values.
- **The rows of `differences.csv`.** [Differences between screen runs](../contracts.md#differences-between-screen-runs) uses these names: the labels, the 23 setting rows and the 20 metric rows in order, when two settings are the same, and when each metric is differenced, with its unit, its decimals, and how the difference is written. Each choice the earlier contracts left open is in the [open questions](#open-questions), with a recommended default.
- **`differences.csv`'s columns.** `difference_unit` and `difference_decimals` cover dates and counts, `reason` adds `unknown_period`, and `declared_reason` is given for every declared change, including one that wasn't observed.

### What R02-T02 specified

On 2026-10-05, R02-T02 specified the review's output in [contracts.md, review output](../contracts.md#review-output):

- **The layout.** `configuration.yaml`, the review configuration byte for byte, claims the output directory. `inputs/<label>/` holds each run's `manifest.json`, `plan.json`, and normalized tables, byte for byte, at their paths in the run, so the copies can be checked against the copied manifest. Then come `normalized/differences.csv`, `report.html`, and `manifest.json`, last.
- **What isn't copied.** The run's configuration, its start and attempt records, its request, its response, and its report. The copied manifest records each one's hash.
- **How it's written.** The review reads and checks each run once, and writes each copy from the bytes it checked. It checks the inputs before the output directory, as `trialfolio report` does.
- **The review manifest.** It records the `review_id`, the `baseline`, and `results`, which say what run each label names: the `artifact_id` of the run's manifest, whether the run is synthetic, its `plan_hash` and `case_id`, whether it has tables, and its response's `artifact_id`. Each copy's entry gives its label. The manifest records the differencing rules as a method with a version, `screen-run-differences` version 1, and counts `differences.csv`'s rows by classification. It has no plan hash, approval, parsers, or reproducibility, which the copied run manifests hold.
- **Labels.** A label names a directory, so the review configuration rejects the device names Windows reserves, such as `con` and `nul`.

The layout follows the defaults of three open questions, which the owner's sign-off confirmed: a review copies no responses; it copies every run's `plan.json`, which a run without tables needs; and it marks each synthetic result. [Included scope](#included-scope) and [required behavior](#required-behavior) named only the manifest and the tables; R02-T03 added the plan to them, which the owner confirmed with the open question on copying it. R02-T02 also added three open questions: whether the configuration is copied with its `run` paths, which rows of `differences.csv` carry `identical_source`, and the code for a `run` directory that doesn't exist.

## User outcome

Compare saved runs against an explicit baseline, and see exactly what differs ([OUT-02](../spec.md#users-and-outcomes)).

## Included scope

- **`trialfolio review <config> --out <dir>`.** An offline comparison of two or more saved Trial Folio runs against an explicit baseline, named in a [review configuration](../contracts.md#review-configuration).
- **A self-contained review.** Each compared run's manifest, plan, and normalized tables are copied into the review output, byte for byte, so the review stands on its own.
- **Settings comparison.** Settings are compared as intended changes or unexplained mismatches, and critical categories are flagged. The settings are Trial Folio's own records of what it sent, so they're `verified`.
- **Metric comparison.** Differences are computed only between comparable values, with explicit units.
- **Outputs:** `differences.csv`, a manifest, a self-contained, script-free HTML report, and the [JSON summary](../contracts.md#json-summary).

## Explicit exclusions

- **Outside results.** Results not produced by Trial Folio, including DataMiner or website exports ([ADR 0005](../adrs/0005-build-on-the-portfolio123-api-only.md)).
- **Network access and provider requests.**
- **Analysis.** Charts, statistical comparison, and any ranking of runs by performance.
- **Assessments.** Statistical validation and trading readiness are reported as "Not assessed".

## Required behavior

1. **Validate before writing.** Validate the configuration, and confirm that every input is a complete Trial Folio run: its manifest is present, and the files it lists match their hashes. Nothing is written until every input passes.
2. **Copy the inputs.** Copy each run's manifest, plan, and normalized tables into the review output, byte for byte, and record their hashes.
3. **Compare settings.**
   - Classify every setting as `same`, `intended_change`, `unexplained_mismatch`, or `unknown`. The settings are the 23 [screen settings](../contracts.md#screen-settings), and [differences between screen runs](../contracts.md#differences-between-screen-runs) says when two are the same.
   - Flag `unexplained_mismatch` and `unknown` in critical categories, including the data source.
   - Flag a declared change that isn't present with `intended_change_not_observed`.
4. **Compare metrics.**
   - Compute differences only between comparable values. Percent-to-percent differences are in percentage points. [Differences between screen runs](../contracts.md#differences-between-screen-runs) gives each metric's rule.
   - Show benchmark-relative metrics side by side without a difference when the benchmarks differ.
   - Never exceed the source precision.
5. **Keep missing values explicit.** An unavailable value stays unavailable, with its reason, and is never zero.
6. **Render the report** following [contracts.md, reports](../contracts.md#reports). Statistical validation and trading readiness read "Not assessed".
7. **Run offline.** Make no network access. Require the [license acknowledgment](../contracts.md#license-acknowledgment), and log as [contracts.md, logging](../contracts.md#logging-and-local-diagnostics) specifies: under `<out>/logs/` once the output directory is claimed.

## Failure and incomplete-data behavior

| Situation | Behavior |
|---|---|
| A result's `run` directory doesn't exist | `input.not_found`, exit 3, as for `trialfolio report`. The message names the result. Nothing is written. The owner confirmed it at sign-off ([open questions](#open-questions)). |
| An input is not a complete run, or its files don't match their manifest hashes | `input.not_a_run`, exit 3. The message names the input and the problem. Nothing is written. |
| An input's schema version has no reader | `artifact.unknown_schema_version`, exit 3; nothing is written |
| Misspelled key, duplicate key, intended change on the baseline, or unknown setting name | `config.invalid`, exit 3; nothing is written |
| Two results point to runs with byte-identical responses | Warning, flagged `identical_source` |
| Output directory exists and isn't empty | `output.not_empty`, exit 4; nothing is modified |
| No license acknowledgment | `license.not_acknowledged`, exit 2 |
| A write fails, or the user interrupts, after the review claims its output directory | `storage.write_failed`, exit 4, or `command.interrupted`, exit 130. No review manifest is left, so the output is visibly incomplete, and the message says so. A manifest that failed after it was published and can't be removed is the one exception, and the message then says that the review reads as complete although the command failed ([review output](../contracts.md#review-output)). |

## Acceptance criteria

[Test pairing](#test-pairing) pairs each criterion with a named check, and with the fixtures and test doubles that check uses. R02-AC15 to R02-AC19 were added by R02-T03, and R02-AC06's `input.not_found` too, and the owner confirmed them at sign-off.

| ID | Criterion |
|---|---|
| R02-AC01 | A two-run review writes the manifest, `differences.csv`, and the report, and exits 0 |
| R02-AC02 | Copied inputs are byte-identical to the runs' files, and the manifest's hashes match |
| R02-AC03 | Different benchmarks are displayed and explicitly flagged, and benchmark-relative metrics aren't differenced across them |
| R02-AC04 | A missing metric is unavailable, with a reason, in the CSV and the report, never zero |
| R02-AC05 | A review completes with network access blocked |
| R02-AC06 | An input that isn't a complete run, or whose files don't match its manifest, fails with `input.not_a_run` and exit 3, and no output directory is created. A `run` directory that doesn't exist fails the same way with `input.not_found`. |
| R02-AC07 | A declared intended change is shown as intended. An undeclared difference in a critical category is flagged as an unexplained mismatch. |

### Test pairing

R02-T09 creates the fixtures and the run builder below, and R02-T10 writes the tests. As in 0.1.0, a task that needs a fixture or a test before then writes it with its code: R02-T04 the review configuration's contract tests, the invalid configurations, and `review-configs/example.yaml`, R02-T05 the input check's core tests, R02-T06 the comparison core's, with the fixtures and the run builder they use, and R02-T07 the review report's, in `tests/core/test_review_report.py`. That module checks the report parts of R02-AC03, R02-AC04, R02-AC07, R02-AC09, R02-AC15, R02-AC16, and R02-AC17 at the core, over runs written with `trialfolio run` and the fake server, read by the input check, and compared by the comparison core. It writes each review's manifest itself, because the command that writes the real one is R02-T08's, as R01-T13's `tests/core/test_report.py` did for a run. R02-T10 adds the interface checks the rows name, through the command. Each test traces to the criterion its row names, and the module names are part of this specification, so a missing pairing is visible.

**Test layout.** 0.1.0's [layout](0.1.0-api-execution.md#test-pairing) stays, with these additions:

```text
tests/
  contract/    the review configuration, and the historical review
  core/        the input check, the comparison core, and the review report
  interface/   the review command
  packaging/   the installed `trialfolio review`
  reference/   a review of the live check's run
  fixtures/    review-configs/ and reviews/, beside 0.1.0's
  support/     the run builder
```

**The runs a review compares.** A review's inputs are complete runs, so its tests use two kinds:

- **Runs built during a test.** The run builder writes them with `trialfolio run`, over the fake Portfolio123 server, from a screen configuration and a response below. They're real `trialfolio run` output, and they exist only in the test's temporary directory. They're never committed: their values are invented, but nothing labels them synthetic, so a committed copy, or a committed review of them, would read as a Portfolio123 backtest ([DSC-04](../disclaimers.md#dsc-04-actual-simulated-and-hypothetical-results)).
- **The committed synthetic run.** 0.1.0's `runs/synthetic-run-1.0.0/`, which `trialfolio demo` wrote and labels synthetic. Trial Folio 0.1.0 wrote it, so a review of it also reads a run that another version wrote. Its copies, each broken one way, are the inputs that fail.

**Fixtures** (`tests/fixtures/`). Every fixture is synthetic, with invented values, and may be committed. Each fixture directory's `README.md` gives each fixture's origin, the layout or schema version it mirrors, its redistribution status, and the criteria it exercises ([fixtures](../contracts.md#fixtures)). 0.1.0's fixtures stay as they are; these are added:

Each review configuration names its runs by paths relative to itself, such as `runs/hold25`, and the test puts it beside the runs it builds. The README gives the screen configuration and the response, or the failed reply, of each run a configuration names. The runs the rows below name are these:

- **The baseline** is `formula.yaml` with `complete.json`, except in `synthetic.yaml`, `synthetic-only.yaml`, and `canaries.yaml`.
- **A changed setting** comes from `holdings-50.yaml`, `slippage-whole.yaml`, or `benchmark-other.yaml`, with `changed-metrics.json` unless its row names another response, so that its response isn't the baseline's.
- **The same settings, written differently,** come from `written-differently.yaml`, with `complete.json`.
- **Each result's response is its own.** No two results of one review have byte-identical saved responses, so `identical_source` flags results only in `shared-response.yaml` and `synthetic-only.yaml`, which are about it, and in `canaries.yaml`, whose shared response puts the warning in the logs R02-AC12 scans.

#### Invalid review configuration cases

The files in `review-configs/invalid/`, by group:

- **Structure:** `misspelled-key`, `misspelled-result-key`, `misspelled-change-key`, `duplicate-key`, `credential-key`, `wrong-kind` (`screen`), `unsupported-schema-version`, and `missing-` plus each required key, with hyphens for underscores: `missing-kind`, `missing-schema-version`, `missing-title`, `missing-baseline`, `missing-results`, `missing-label`, `missing-run`, `missing-setting`, and `missing-reason`. Also, for the YAML rules that apply to [every configuration file](../contracts.md#configuration-files): `null-value`, `anchor-alias`, `explicit-tag`, `non-text-key`, `two-documents`, and `not-a-mapping`.
- **Results:** `one-result`, `baseline-not-a-label`, `duplicate-label`, `intended-change-on-baseline`, and `empty-intended-changes` (`intended_changes: []`, which is rejected, as an [open question](#open-questions) settled).
- **Settings:** `unknown-setting` (`max_holding`), `undeclarable-setting` (`commission`), and `setting-listed-twice`.
- **Labels:** `label-uppercase` (`Hold25`), `label-leading-hyphen` (`-hold25`), `label-too-long` (65 characters), `label-with-dot` (`hold.25`), and `label-device-name` (`nul`). The contract test also checks each of the other 21 device names.
- **Text:** `empty-title`, `title-too-long` (201 characters), `purpose-too-long` (2,001 characters), `blank-purpose` (`'   '`), `blank-description`, `description-too-long` (501 characters), `empty-reason`, `blank-reason`, `reason-too-long` (501 characters), and `empty-run`.
- **Coerced values,** which strict validation rejects: `label-number` (`25`), `baseline-number` (`25`), and `setting-number` (`5`).

## Open questions

R02-T03 recommended a default for each question below, and the owner's sign-off on 2026-10-05 confirmed them all, as it did 0.1.0's. Each default is now a requirement, and each alternative is kept for the record. R02-T03 added the last four.

| Question | Impact | Recommended default | Resolve by |
|---|---|---|---|
| Should a review accept runs written by different Trial Folio versions? | Compatibility | Yes, when each run's schema version has a reader. The committed demo run, which Trial Folio 0.1.0 wrote, is one of the tests' inputs (R02-AC16). | Confirmed at the owner's sign-off (2026-10-05) |
| Should a review copy full responses, or only manifests and normalized tables? | Output size, self-containment, and what a shared review holds | Neither the response nor the request. The review copies each run's manifest, plan, and normalized tables ([review output](../contracts.md#review-output)). The copied manifest records each file's hash, the response's included, and the review manifest's `results` record each response's, which is all `identical_source` needs. A response holds Portfolio123's data, including per-period series a review doesn't compare, and a review may be shared ([D-14](../spec.md#decisions)). | Confirmed at the owner's sign-off (2026-10-05) |
| Can a review include a run without normalized tables, because its attempt didn't succeed or its response was invalid? | Whether failed runs, which INV-01 keeps, can be compared | Yes. Its settings are compared from its plan, as its own report shows them. The review copies every run's `plan.json`, which also holds the run's title and purpose and its wrapper's versions ([review output](../contracts.md#review-output)). Its plan's rows stand in for `settings.csv`'s, with the plan's flags ([differences between screen runs](../contracts.md#differences-between-screen-runs)). Every metric is `unavailable`, with `input_unavailable`, and the report says why the run has no tables, from its copied manifest's `error`. The alternative was to copy `plan.json` only for a run without tables. | Confirmed at the owner's sign-off (2026-10-05) |
| Can a review include the run `trialfolio demo` writes? | Synthetic values must never read as Portfolio123's ([DSC-04](../disclaimers.md#dsc-04-actual-simulated-and-hypothetical-results)) | Yes, alone or with real runs. The review manifest marks each synthetic result in `results`, and is `synthetic` when any result is ([review output](../contracts.md#review-output)). The report labels each synthetic result, as the demo's own report does, and when any is synthetic, says which before any result, so no difference reads as Portfolio123's. | Confirmed at the owner's sign-off (2026-10-05) |
| Are the benchmark's own metrics differenced when the runs' benchmarks differ? | Whether the gap between two different benchmarks' returns reads as a change | No. Rows 15–20 are differenced only when the runs' `benchmark` settings are the same, and are otherwise `not_comparable`, with `different_benchmark` ([differences between screen runs](../contracts.md#differences-between-screen-runs)). | Confirmed at the owner's sign-off (2026-10-05) |
| How are the coverage rows compared? | Whether a review shows how far coverage moved | Coverage is the period, so the period rule doesn't apply to it. Dates are differenced in `days`, and `coverage_periods` in `count`, both with 0 decimal places. | Confirmed at the owner's sign-off (2026-10-05) |
| What reason does a metric get when a run's period is unknown? | An unknown period isn't a different one | A new reason, `unknown_period` | Confirmed at the owner's sign-off (2026-10-05) |
| Which reason is given when several apply? | `reason` holds one code | The first of `different_unit`, `different_benchmark`, and `different_period` or `unknown_period`. The setting rows show every difference. | Confirmed at the owner's sign-off (2026-10-05) |
| How is a difference rounded to the smaller decimal count, and how is it written? | The same inputs must always give the same `differences.csv` | Half to even, the default of Python's `decimal`, which doesn't lean either way. The count is the values' recorded `source_decimals`. Saving drops trailing zeros, so `12.5` has one decimal place even when it was requested at 4, but a whole number saved as a float keeps its `.0`, so `12.0` has one too. A difference is written with exactly that many decimal places, as `0.10`, so its digits match `difference_decimals`, and a zero difference is written without a sign, never `-0.0` ([differences between screen runs](../contracts.md#differences-between-screen-runs)). | Confirmed at the owner's sign-off (2026-10-05) |
| Which flags does a setting row carry, and which set `flagged`? | Whether `flagged` stays a signal or turns into noise | A row carries the flags either run's `settings.csv` row has, or its plan's row for a run without tables, and its comparison's own. `flagged` is true for `critical_unexplained_mismatch`, `critical_unknown`, `intended_change_not_observed`, `coverage_mismatch`, `unsupported_value`, and `identical_source`. `not_snapshotted` and `inferred_default` don't set it. Every screen run's `universe` row is `not_snapshotted`, and its `data_vendor` and `risk_stats_period` rows are `inferred_default`, so those would flag every review. A `ranking` row is `not_snapshotted` only for a ranking system named or given by ID, and isn't flagged either: a ranking system edited between two runs doesn't show as a change, just as a universe edited between them doesn't. The report lists each external reference instead. The alternative was to have `not_snapshotted` set `flagged` on the `ranking` row only. | Confirmed at the owner's sign-off (2026-10-05) |
| Should a review copy its configuration byte for byte, though its `run` paths can name the user? | Whether a shared review shows where the user keeps runs ([D-14](../spec.md#decisions)) | Yes. It's the source of the baseline, the labels, and each declared change's reason ([INV-04](../spec.md#enduring-invariants)). The manifest and the report never repeat the paths, and the user guide will recommend paths relative to the configuration. The alternative was to record the configuration's parsed content without its paths, which loses the source's bytes. | Confirmed at the owner's sign-off (2026-10-05) |
| Which rows of `differences.csv` carry `identical_source`? | Where a reader of the table learns that two results have one response | Every metric row of a result whose saved response is byte-identical to another result's, the baseline's included. So any two results with one response are flagged, as the [failure behavior](#failure-and-incomplete-data-behavior) requires. Identical responses give identical metrics. Against the baseline's response, the flag says that the zero differences come from one response, not from two runs that agree. On two other results that share a response, it says that their rows are the same because they come from one response. The review manifest's `results` and the report name the results that share each response. The alternative was to flag only a result whose response is the baseline's. That would leave two other results with one response unflagged, narrowing the failure behavior's settled row. | Confirmed at the owner's sign-off (2026-10-05) |
| Is a `run` directory that doesn't exist `input.not_found` or `input.not_a_run`? | Whether `review` and `trialfolio report` give the same code for the same problem | `input.not_found`, exit 3, as `trialfolio report` gives ([running the commands](../contracts.md#cli-behavior)). The message names the result's label. R02-T03 added it to the failure table and R02-AC06. | Confirmed at the owner's sign-off (2026-10-05) |
| Which version of the JSON summary does 0.2.0 write? | Scripts that read the summary. The release kept the summary at 1.0.0 and added the review's counts, but the summary's own rule adds keys only in a minor version ([JSON summary](../contracts.md#json-summary)). The committed `schemas/json-summary-1.0.0.schema.json` allows no other key: its `command` has no `review`, its `ids` no `review_id`, and its `counts` neither the review's counts nor any other key. | 1.1.0, for every command: 1.0.0, with `review` in `command`, `review_id` in `ids`, and the review's `counts`. Each 1.0.0 key keeps its meaning, so a 1.0.0 summary with its version changed to 1.1.0 is a valid 1.1.0 summary. The 1.0.0 schema stays committed beside 1.1.0's, with its bytes unchanged, because it says what 0.1.0 prints, for scripts written against it. So the model that generates it keeps its name, and the 1.1.0 model takes a new one ([JSON summary](../contracts.md#json-summary), [schema generation](../contracts.md#schema-generation-and-drift)). 0.1.0's check of R01-AC18, `tests/interface/test_json_summary.py`, then checks each command's summary against the 1.1.0 schema and version, with this decision as the stated reason, and the user guide names the 1.1.0 schema. The alternative was to change the committed 1.0.0 schema, which would change a published version. | Confirmed at the owner's sign-off (2026-10-05) |
| When does the JSON summary hold a `review_id`? | Linking a summary to its output. The summary leaves out a key that has no value. | Once the review has claimed its output directory: on success, and on a failure after the claim, when `<out>/logs/` holds the events that carry it. A failure before the claim writes nothing, so it has none, as a run with no attempt record or start record has no `attempt_id`. | Confirmed at the owner's sign-off (2026-10-05) |
| Do logs and warnings name a result's label? | Whether the [log content rule](../contracts.md#logging-and-local-diagnostics) covers labels | No. A label is the user's own text, a configuration value, which logs never hold. A logged event, and so a warning on stderr, names a result by its position in `results`, such as "result 2". The report and the manifest give its label. An error's full message, on stderr and in the JSON summary, names the label, and its logged message, which holds only what logs may, gives the position instead ([errors](../contracts.md#errors)). A copy's path, `inputs/<label>/…`, holds the label too, and 0.1.0's `ArtifactStore` logs the path of each file it writes, and names it in its errors' logged messages. So for a copy, the store logs a name with the result's position instead, which R02-T08 adds ([review output](../contracts.md#review-output)). The alternative was to log labels as identifiers, since their pattern can't hold a formula, which leaves the store as it is. | Confirmed at the owner's sign-off (2026-10-05) |
| May `intended_changes` be an empty list? | One way to write a result that declares nothing | No, it's `config.invalid`. A result that declares nothing leaves the key out, as any optional key with no value is left out ([configuration files](../contracts.md#configuration-files)), and a list that's given holds at least one entry, as `rules` does. The alternative was to accept an empty list as declaring nothing. | Confirmed at the owner's sign-off (2026-10-05) |
