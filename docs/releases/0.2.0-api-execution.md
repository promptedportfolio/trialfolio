## Completing this specification

**What's missing, in order:**

1. **Reference payload.** Procure it (R02-T01) and document its layout and mapping to the result contract (R02-T02). This fixes the verified settings subset and the metric identifiers.
2. **The `kind: screen` configuration format (R02-T03).** Specify every key, type, unit, and whether it's required. Only the vendor may be omitted ([D-16](../spec.md#decisions)). Add a validated example.
3. **The plan (R02-T04).** Specify its contents and the non-interactive approval option. The recommended default is `--approve <plan-hash>`.
4. **Normalization (R02-T02).** Specify how payload fields map to normalized metrics, units, and provenance.
5. **Test pairing (R02-T05).** Pair each acceptance criterion with a fixture or integration check, and finalize the verification commands.
6. **Open questions (R02-T05).** Resolve them, or confirm their defaults.

**How to complete it:**

- **Read first:** [AGENTS.md](../../AGENTS.md), [spec.md](../spec.md), [contracts.md](../contracts.md), and the methodology and ADR sections this file references.

## User outcome

Execute one supported screen backtest and keep the relationship between its settings and its results ([OUT-02](../spec.md#users-and-outcomes)).

## Included scope

- `trialfolio run <config> --out <dir>`: plan, approve, execute, capture, normalize, and report one long-only stock screen backtest through `p123api`'s `screen_backtest`.
- A narrow `kind: screen` configuration covering an inline screen only. The subset limited to settings verified in R02-T02 is:
  - universe, rules, and ranking (an existing system by name or ID, or a single formula)
  - maximum holdings, benchmark, start date, end date, rebalance frequency, transaction price, slippage, point-in-time method, and precision
  - data vendor: FactSet only, and optional ([D-16](../spec.md#decisions))
- A plan with its hash, a request budget, and the categories of data sent, all shown before execution. Execution requires the approved hash ([REQ-04](../spec.md#enduring-requirements)).
- Attempt records with the redacted request, the full decoded payload, timing, the wrapper version, and provider metadata (`cost`, `quotaRemaining`), saved before any normalization.
- The same result contract and report as 0.1.0. Review configurations MAY list a Trial Folio run directory as a result, so archived runs can be compared and re-rendered offline with `trialfolio review`.
- A migration example that turns a DataMiner ScreenBacktest configuration into a `kind: screen` configuration.

## Explicit exclusions

- Saved screens by ID, short, long/short, or hedged methods, ETF screens, and ranking definitions given as nodes or XML. The last would mutate `APIRankingSystem`.
- Compustat, or any vendor other than FactSet ([D-16](../spec.md#decisions)).
- Rolling screens, rank performance, simulations, and any other endpoint.
- Automatic retry of a charged request.
- Multiple cases. Experiments arrive in [0.3.0](0.3.0-experiments.md).
- Interpreting the per-period series beyond preserving it in the payload and establishing coverage.
- Every DataMiner option, and any clone of its interface.

## Supported inputs and examples

```text
trialfolio run screen.yaml --out runs/baseline/
```

The `kind: screen` structure is not specified yet; see [Completing this specification](#completing-this-specification), step 2. A single-formula ranking is recommended, because it is fully recorded in the configuration. A ranking by name or ID refers to a mutable account object.

## Required behavior

1. **Validate strictly.** Reject any setting outside the verified subset before a plan is built. The start date, end date, benchmark, and slippage MUST be explicit. There is no default of "today" and no default of zero cost.
   - The vendor MAY be omitted, as in DataMiner. Trial Folio then leaves it out of the request, as DataMiner does, and the plan shows FactSet as an inferred default. R02-T01 confirms that the provider's default is FactSet.
   - A vendor other than FactSet fails with `config.invalid`.
2. **Show the plan.** Show the resolved request, what will be sent to Portfolio123, the request budget, the documented credit cost, and the plan hash.
   - Portfolio123 documents a cost of 5 credits for a screen backtest. Whether failed requests are charged is unverified, so failed and uncertain attempts are treated as possibly charged.
   - Execute only with the matching approved hash.
3. **Make attempts visible.** Configure the wrapper for one HTTP attempt per call. Write a durable `running` attempt record before sending. Request decoded JSON (`to_pandas=False`).
4. **Capture first.** Save the complete decoded payload and provider metadata durably before any normalization or validation of its content. A payload that later fails validation is kept and flagged.
5. **Redact.** The saved request contains no credentials. Never log, serialize, or save wrapper exception or response objects. Keep only the status code and a sanitized message.
6. **Normalize.** Map the payload to the 0.1.0 result contract. Values Trial Folio captured itself are `verified`.
7. **Record mutable references.** For a ranking or universe given by name or ID, record it as an external reference. Record whether its definition was snapshotted, and label reproducibility incomplete when it was not.
8. **Label costs honestly.** No commission parameter is documented. Commission is recorded as "not modeled by this provider path", never as zero.
9. **Report.** Produce the same report as 0.1.0, with execution details.

## Failure and incomplete-data behavior

| Situation | Behavior |
|---|---|
| Missing credentials | `provider.auth_failed`, exit 5, before any request |
| Authentication rejected (400, 401, 402, or 406) | `provider.auth_failed`, exit 5. The message is actionable, for example "invalid ID/key" or "paying subscription required". The attempt is recorded as `failed`. |
| Quota exhausted (402 on a request) | `provider.quota_exceeded`, exit 5. The attempt is `failed`, possibly charged. |
| Setting outside the verified subset | `config.invalid` (or `provider.unsupported_capability` if the provider rejects it), exit 3 or 5. No request is sent in the first case. |
| Connection error before a response | The attempt is `failed`, with its charge status unknown |
| Read timeout, or the process dies after sending | The attempt is `unknown`, reported as uncertain and never retried automatically. The error is `provider.outcome_unknown`, exit 5. |
| Response fails validation | The payload is saved and the attempt is `succeeded` for capture. The result is flagged `provider.response_invalid`, exit 5, and the report shows the normalized result as unavailable. |
| Approval missing or hash mismatch | `plan.approval_required`, exit 2, and no request is sent |

`provider.outcome_unknown` is defined in [contracts.md](../contracts.md#errors).

## Required outputs

`manifest.json`, `plan.json`, and `cases/<case_id>/attempts/<attempt_id>/`, which holds `attempt.json`, `request.json` (redacted), and `response.json` (the decoded payload). Also the normalized CSVs, `report.html`, and `logs/`.

## Acceptance criteria

| ID | Criterion |
|---|---|
| R02-AC01 | The plan shows the resolved request, budget, and hash, and no request is sent without the matching approval |
| R02-AC02 | A misspelled or unsupported setting is rejected before any request |
| R02-AC03 | The complete available provider payload, including `cost` and `quotaRemaining` when present, is saved before normalization |
| R02-AC04 | No credential canary appears in any artifact or log, including after a simulated authentication failure |
| R02-AC05 | Authentication, quota, unsupported-capability, and response-validation errors each give their documented code, exit code, and actionable message |
| R02-AC06 | A simulated read timeout records an `unknown` attempt that is not retried |
| R02-AC07 | The attempt log records exactly one attempt per HTTP request, using a test double at the client boundary |
| R02-AC08 | `trialfolio review` re-renders an archived run with network access blocked, and the result matches the saved normalized data |
| R02-AC09 | A missing end date or slippage is a configuration error, never today or zero |
| R02-AC10 | A ranking given by name records an external reference with its snapshot status, while a single-formula ranking is fully recorded |
| R02-AC11 | The 0.1.0 acceptance criteria still pass |
| R02-AC12 | A recorded real integration check with the owner's account succeeds within its budget, and its output is archived locally and regenerated offline. It is opt-in and never part of default CI. |
| R02-AC13 | An omitted vendor is left out of the request and shown in the plan as FactSet, an inferred default. An explicit `FactSet` is sent as given. `Compustat` fails with `config.invalid` before any request. |
